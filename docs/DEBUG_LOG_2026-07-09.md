## 1. 겪은 문제와 원인

### 1-1. `/dev/motor`, `/dev/ttyimu` 링크가 안 생김
- **원인:** 설치돼 있던 udev 규칙이 옛 장치 기준(라이다는 포트위치 KERNELS, 모터는 옛 시리얼)이라 현재 하드웨어와 안 맞음. `dialout` 그룹 미가입 + 규칙에 `MODE=0666` 누락으로 권한도 취약.
- **증상:** `/dev/rplidar`, `/dev/motor` 심볼릭 링크 미생성. 노드가 포트를 못 잡음.

### 1-2. 포트 매핑이 실제로 뒤바뀌어 있었음 (모터 ↔ IMU)
- **핵심 발견:** `/dev/motor` 로 잡은 포트에서 `*ROLL,PITCH,YAW,...`(EBIMU 포맷)가 스트리밍됨.
  즉 그 포트는 **IMU** 였다. 모터 드라이버가 이 포트를 열어 JSON 파싱을 시도 → 계속 실패 →
  rpm 피드백이 항상 0, 모터 제어 불능. (과거 "EIO"/"토크 없음"의 진짜 뿌리)
- **확정 방법:** 각 포트를 python으로 raw 읽기.
  - IMU(CP210x): `*...` 텍스트를 **계속** 흘림.
  - 모터(CH340): 평소 무응답, **DDSM 명령을 보내야** 응답(hex 프레임 `0x01,0xA0,...`).
  - 라이다(CP210x): 바이너리.

### 1-3. EKF 가 NaN 으로 발산 → `/odom` 이 nan
- **증상:** `ekf_filter_node` 가 `Critical Error, NaNs were detected ... poorly conditioned covariances` 반복,
  `odom→base_link` TF 가 `nan`.
- **진짜 원인:** 우리가 **레거시 런치 `real_robot.launch.py`** 를 띄웠고, 그게 쓰는
  `relayrobot_driver/motor_node_1.py` 의 odom 공분산이 `[1e-9]*36`(≈0) 이었다.
  robot_localization 은 공분산 0 을 "무한 신뢰"로 해석 → 공분산 행렬이 특이(singular) → 역행렬 NaN.
- **오해했던 것:** 처음엔 "모터에 전원 인가해서 NaN 나나?" 로 의심했지만, `/odom_raw` 는 값이 멀쩡했고
  NaN 은 기동 26초부터 이미 발생 → 전원과 무관, **EKF 입력 공분산 문제**였다.

## 2. 왜 헷갈렸나 (진짜 교훈)

- **활성 런치와 레거시 런치가 공존**한다.
  - ✅ 정식(원격 최신): `real_robot_260519.launch.py` → `relayrobot_description/.../real_robot_driver_260519.py`
    → odom 공분산 정상(pose 0.05 / yaw 0.1). **NaN 안 남.**
  - ❌ 레거시: `real_robot.launch.py` → `relayrobot_driver/motor_node_1.py` → 공분산 `1e-9`. **NaN 남.**
  레거시 런치를 띄우는 바람에, 이미 고쳐진 문제를 "새 버그"로 착각하고 다시 디버깅했다.

- **원격에 이미 같은 작업이 올라와 있었다.**
  다른 세션/PC 에서 같은 하드웨어 문제(udev 식별, IMU 공분산+바이어스+파서, 새 260519 드라이버)를
  이미 해결해 push 해둔 상태. 로컬에서 중복으로 손대고 push 하려다 divergence(ahead 3 / behind 21) 발생.
  - 로컬 udev 스크립트(시리얼·순차연결) = 원격(chip/product) 과 **중복/상충** → 폐기.
  - 로컬 IMU 공분산 수정 = 원격이 이미 함 → **중복**.
  - 로컬이 고친 `motor_node_1.py` 공분산 = 활성 런치가 **안 쓰는 레거시 파일** → 무의미.
  → 결국 `git reset --hard origin/main` 으로 원격에 맞추고 로컬 작업은 전부 버림.
