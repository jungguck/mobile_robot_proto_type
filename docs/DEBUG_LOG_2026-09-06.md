## 1. SSH 키 인증

PC 의 공개키를 젯슨 `~/.ssh/authorized_keys` 에 추가했다.

```bash
$ ssh -o BatchMode=yes robot "hostname; whoami"
frlab
frlab
```

`BatchMode=yes` 는 **비밀번호 입력 자체를 금지**하는 옵션이다. 이걸로 통과했다는 건
키 인증이 확실히 먹었다는 뜻이다. 단순히 `ssh robot` 이 붙는 것보다 강한 증거이므로,
키 등록을 확인할 땐 항상 이 옵션을 쓴다.

PC 의 `~/.ssh/config` (이미 있음):

```
Host robot
    HostName 172.30.1.45
    User frlab
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
    ServerAliveCountMax 3
    ForwardX11 yes
```

> ⚠️ `HostName` 이 **DHCP 로 받은 IP** 다. 공유기가 주소를 바꾸면 여기도 고쳐야 한다.
> 근본 해결은 `REMOTE_ACCESS.md` 2-B (avahi 인터페이스 고정 → `frlab.local`) 인데
> **아직 안 고쳤다.** 다음에 IP 가 바뀌어서 접속이 안 되면 그것부터 의심할 것.

## 2. `~/.bashrc` — 비대화형 셸 함정

`ssh robot '<명령>'` 로 ROS 명령을 바로 쏘고 싶었는데, 처음엔 안 됐다.

```bash
$ ssh robot 'echo "ROS_DISTRO=[$ROS_DISTRO]"'
ROS_DISTRO=[]        # ← 비어 있다
```

**원인:** Ubuntu 기본 `~/.bashrc` 6행에 이게 있다.

```bash
case $- in
    *i*) ;;
      *) return;;      # ← 비대화형이면 여기서 즉시 반환
esac
```

`ssh robot '<명령>'` 는 **비대화형** 셸이라 이 줄에서 끝나버린다. 그래서 파일 **끝**에
`source /opt/ros/humble/setup.bash` 를 붙이면 대화형 접속(`ssh robot`)에서만 먹고,
원격 한 줄 명령에서는 영영 안 먹는다.

**해결:** ROS 블록을 `.bashrc` **맨 앞**(가드보다 위)으로 옮겼다.

```bash
# ── ROS 2 Humble 환경 ───────────────────────────────
source /opt/ros/humble/setup.bash

# 워크스페이스 오버레이 — 아직 빌드 전이면 조용히 건너뛴다
if [ -f "$HOME/mobile_robot_proto_type/install/setup.bash" ]; then
  source "$HOME/mobile_robot_proto_type/install/setup.bash"
fi

export ROS_DOMAIN_ID=0        # PC 쪽과 반드시 같아야 토픽이 보인다
export ROS_LOCALHOST_ONLY=0   # 0 이어야 원격에서 토픽이 보인다
```

백업: `~/.bashrc.bak.20260906`

> **주의 — 맨 앞에 둘 때 지켜야 할 규칙: 아무것도 출력하면 안 된다.**
> 비대화형 셸은 `scp`/`sftp` 도 쓴다. 여기서 한 글자라도 출력되면 **scp 가 깨진다.**
> `setup.bash` 는 조용해서 문제없다. 확인도 했다:
> ```bash
> $ scp -o BatchMode=yes /tmp/scptest.txt robot:/tmp/scptest.txt
> scp 업로드 OK
> ```
> 나중에 이 블록에 `echo` 를 추가하고 싶어지면 참으라는 뜻이다.

## 3. numpy 2 ↔ transforms3d 충돌 (오늘의 진짜 버그)

빌드 전 의존성을 훑다가 이게 나왔다.

```
>>> import transforms3d
  File "/usr/lib/python3/dist-packages/transforms3d/quaternions.py", line 26
    _MAX_FLOAT = np.maximum_sctype(np.float)
AttributeError: `np.maximum_sctype` was removed in the NumPy 2.0 release.
```

`relayrobot_driver` 와 `relayrobot_description` 이 `tf_transformations` 에 의존하는데,
그게 내부적으로 `transforms3d` 를 쓴다. **그대로 뒀으면 드라이버 노드가 import 에서 죽었다.**

### 왜 이렇게 됐나

| 경로 | 패키지 | 버전 | 출처 |
|---|---|---|---|
| `~/.local/lib/python3.10/site-packages` | numpy | **2.2.6** | pip (cvxpy 의존으로 딸려옴) |
| `/usr/lib/python3/dist-packages` | numpy | 1.21.5 | apt (Humble 이 기대하는 것) |
| `/usr/lib/python3/dist-packages` | transforms3d | 0.3.1 | apt (numpy 1 시절 코드) |

`~/.local` 이 `/usr/lib` 보다 우선하므로 numpy 2 가 이긴다. 그런데 apt 의
`transforms3d 0.3.1` 은 numpy 2 에서 제거된 API 를 쓴다. 여기서 터진 것이다.

### 왜 numpy 를 1.x 로 되돌리지 않았나

**`~/.local` 의 numpy 2 는 tube MPC 스택(`cvxpy`, `osqp`, `clarabel`, `polytope`)이 요구하는 것이다.**
되돌리면 MPC 쪽이 통째로 깨진다. 그래서 **반대 방향으로 고쳤다.**

```bash
pip3 install --user --upgrade "transforms3d>=0.4.2"
```

0.4.2 는 numpy 2 를 지원한다. `~/.local` 에 깔리면서 apt 의 0.3.1 을 똑같이 가려준다.
양쪽 다 산다:

```
transforms3d 0.4.2 / numpy 2.2.6
tf_transformations OK
  euler->quat(0,0,pi/2) = [0.0, 0.0, 0.7071, 0.7071]
cvxpy 1.7.5 OK
```

> **규칙: 이 젯슨에서 `pip install numpy` 로 버전을 내리지 말 것.**
> ROS 쪽 라이브러리가 numpy 2 에서 깨지면, numpy 를 내리는 게 아니라
> **그 라이브러리를 올리는 쪽으로** 푼다.

## 4. 패키징 버그 2건 (rosdep / ros2 run 을 막고 있던 것)

### 4-1. `package.xml` 의 `<buildtool_depend>ament_python</buildtool_depend>`

`rosdep check` 가 여기서 멈췄다.

```
ERROR[ebimu_pkg]: Cannot locate rosdep definition for [ament_python]
ERROR[mpc_tubempc_bridge]: Cannot locate rosdep definition for [ament_python]
```

**`ament_python` 이라는 rosdep 키는 존재하지 않는다.** 파이썬 패키지의 빌드 타입은
`<export>` 안에서 선언하는 것이고, 의존성으로 적는 게 아니다. 두 줄이 다 있었다:

```xml
<buildtool_depend>ament_python</buildtool_depend>   <!-- ← 틀렸다. 삭제 -->
...
<export>
  <build_type>ament_python</build_type>             <!-- ← 이게 맞는 선언 -->
</export>
```

패키지 5개(`ebimu_pkg`, `gui_py`, `mpc_tubempc_bridge`, `relayrobot_description`,
`relayrobot_driver`)에서 첫 줄을 지웠다. 이후:

```
$ rosdep check --from-paths src --ignore-src -r
All system dependencies have been satisfied
```

> `colcon build` 는 rosdep 을 안 쓰기 때문에 **빌드는 그냥 됐었다.** 그래서 여태
> 안 드러난 것이다. 새 PC·새 젯슨에 세팅할 때만 터지는 종류의 버그다.

### 4-2. `mpc_tubempc_bridge` 에 `setup.cfg` 누락

빌드는 성공하는데 `ros2 pkg executables mpc_tubempc_bridge` 가 **아무것도 안 뱉었다.**
`setup.py` 의 `entry_points` 는 멀쩡했는데도.

빌드 로그를 보니:

```
Installing mpc_tubempc_bridge script to .../install/mpc_tubempc_bridge/bin
```

**`bin/` 에 깔렸다.** ROS 2 는 `lib/<패키지명>/` 만 본다. 그래서 못 찾은 것이다.

원인은 `setup.cfg` 부재였다. 다른 5개 패키지엔 다 있는데 이것만 없었다:

```ini
[develop]
script_dir=$base/lib/mpc_tubempc_bridge
[install]
install_scripts=$base/lib/mpc_tubempc_bridge
```

이 파일이 콘솔 스크립트 설치 위치를 `lib/<패키지>/` 로 돌려놓는다. 만들어 넣고 재빌드하니:

```
$ ros2 pkg executables mpc_tubempc_bridge
mpc_tubempc_bridge mpc_tubempc_bridge
mpc_tubempc_bridge mpc_tubempc_path_planner
```

> **증상으로 기억할 것: "빌드는 되는데 `ros2 run` 이 패키지를 못 찾는다" → `setup.cfg` 부터 본다.**
> `ros2 pkg create` 가 자동 생성해주는 파일이라, 손으로 만든 패키지에서만 빠진다.

## 6. 원격 운용 준비 (`setup_remote_ops.sh`)

실행했다. 설치된 것:

| 항목 | 경로 |
|---|---|
| udev 규칙 | `/etc/udev/rules.d/99-robot-devices.rules` |
| 무비밀번호 종료 권한 | `/etc/sudoers.d/010-robot-poweroff` |
| 안전 종료 명령 | `/usr/local/bin/robot-off` |

SD 카드(`/dev/mmcblk0p1`, ext4) 저널 활성 / 상태 clean 확인.

### sudo 티켓 함정 — 이 스크립트는 `ssh robot '...'` 로 못 돌린다

처음에 이렇게 했더니 실패했다:

```bash
ssh robot 'echo "1234" | sudo -S -v && ./scripts/setup_remote_ops.sh'
#   → sudo 인증 OK
#   → ==> sudo 권한 확인 ... sudo: a password is required   ← 스크립트 안에서 또 물어봄
```

**원인:** tty 가 없으면 sudo 티켓이 **부모 프로세스 ID(ppid) 기준**으로 잡힌다.
바깥 셸에서 인증해도 스크립트는 다른 프로세스라 티켓을 물려받지 못한다.
(같은 셸에서 이어 실행하는 `sudo -n apt-get` 은 되는데 스크립트는 안 되는 이유가 이것이다.)

**해결 — pty 를 강제로 붙인다 (`ssh -tt`):**

```bash
printf '1234\n' | ssh -tt robot 'cd ~/mobile_robot_proto_type && ./scripts/setup_remote_ops.sh'
```

> 앞으로도 **젯슨에서 sudo 를 쓰는 스크립트를 원격 실행할 땐 `ssh -tt`** 를 쓴다.
> 출력에 `\r` 이 섞이므로 읽기 힘들면 `| tr -d '\r'` 를 붙인다.

### 등록된 USB 별명 — 꽂기 전에 미리 잡아둔 것

```
모터   1a86:55d3                  ->  /dev/motor
라이다 10c4:ea60 (CP2102N)        ->  /dev/rplidar
IMU    10c4:ea60 (CP2102)         ->  /dev/ttyimu
```

이제 **꽂는 순서와 무관하게** 위 이름으로 잡힌다. `ttyUSB0/1/2` 가 순서마다 바뀌던 문제가
사라진다. 코드에서도 `/dev/ttyUSB*` 가 아니라 이 이름을 쓸 것.

## 7. 원격 개발 흐름 (앞으로 이렇게 한다)

```
   [ PC ]                                 [ 젯슨 robot ]
   코드 수정 · git commit · push           실제 실행 (모터/IMU/라이다가 여기 달림)
        │                                        │
        ├── git push ───► GitHub ───► git pull ──┤   코드는 git 으로 옮긴다
        ├── ssh robot '<명령>' ─────────────────►┤   명령은 ssh 한 줄로
        └──◄──── DDS (같은 공유기 대역) ─────────┘   토픽은 네트워크로 그대로 흐른다
```

**코드 반영:**
```bash
# PC
git commit -am "..." && git push

# 젯슨
ssh robot 'cd ~/mobile_robot_proto_type && git pull'
# 파이썬만 고쳤으면 여기서 끝. C++/launch/setup.py 를 건드렸으면:
ssh robot 'cd ~/mobile_robot_proto_type && colcon build --symlink-install'
```

> **`scp` 로 파일을 직접 복사하지 말 것.** 금방 어긋난다. 오늘도 빌드를 막고 있어서
> 어쩔 수 없이 양쪽에 같은 수정을 손으로 넣었는데, 이건 예외이자 마지막이어야 한다.
> (`DEBUG_LOG_2026-09-03.md` 1절의 교훈과 같은 이야기다)

**시각화(rviz) 는 두 가지:**

| 방법 | 어떻게 | 평가 |
|---|---|---|
| X11 포워딩 | 젯슨에서 rviz 실행, 화면만 전송 (`ForwardX11 yes` 로 이미 가능) | WiFi 로는 **매우 느리다.** `hw_test` 같은 가벼운 GUI 용 |
| **DDS** | PC 에도 Humble 설치 → `ROS_DOMAIN_ID` 를 **0** 으로 맞춤 → PC 의 rviz 가 젯슨 토픽을 직접 구독 | **이쪽이 정답.** 같은 공유기 대역이면 별도 설정 불필요 |

PC 쪽 Humble 은 **아직 안 깔았다.** 다음 세션 후보 작업.

**종료 — 절대 전원을 그냥 뽑지 말 것:**
```bash
ssh robot robot-off      # 모터 정지 → 노드 종료 → sync → 전원 차단
ping 172.30.1.45         # 응답 끊기고 20초 더 기다린 뒤 어댑터 분리
```
SD 카드 부팅이라 갑작스런 전원 차단에 약하다. 실제로 한 번 깨진 적이 있다.
