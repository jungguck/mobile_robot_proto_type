## 1. SSH 키 인증

PC 의 공개키를 젯슨 `~/.ssh/authorized_keys` 에 추가했다.

```bash
$ ssh -o BatchMode=yes robot "hostname; whoami"
frlab
frlab
```

`BatchMode=yes` 는 **비밀번호 입력 자체를 금지**하는 옵션이다. 이걸로 통과했다는 건
키 인증이 확실히 먹었다는 뜻이다. 단순히 `ssh robot` 이 붙는 것보다 강한 증거이므로,
키 등록을 확인할 땐 항상 이 옵션을 쓴다.

PC 의 `~/.ssh/config` (이미 있음):

```
Host robot
    HostName 172.30.1.45
    User frlab
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 30
    ServerAliveCountMax 3
    ForwardX11 yes
```

> ⚠️ `HostName` 이 **DHCP 로 받은 IP** 다. 공유기가 주소를 바꾸면 여기도 고쳐야 한다.
> 근본 해결은 `REMOTE_ACCESS.md` 2-B (avahi 인터페이스 고정 → `frlab.local`) 인데
> **아직 안 고쳤다.** 다음에 IP 가 바뀌어서 접속이 안 되면 그것부터 의심할 것.

## 2. `~/.bashrc` — 비대화형 셸 함정

`ssh robot '<명령>'` 로 ROS 명령을 바로 쏘고 싶었는데, 처음엔 안 됐다.

```bash
$ ssh robot 'echo "ROS_DISTRO=[$ROS_DISTRO]"'
ROS_DISTRO=[]        # ← 비어 있다
```

**원인:** Ubuntu 기본 `~/.bashrc` 6행에 이게 있다.

```bash
case $- in
    *i*) ;;
      *) return;;      # ← 비대화형이면 여기서 즉시 반환
esac
```

`ssh robot '<명령>'` 는 **비대화형** 셸이라 이 줄에서 끝나버린다. 그래서 파일 **끝**에
`source /opt/ros/humble/setup.bash` 를 붙이면 대화형 접속(`ssh robot`)에서만 먹고,
원격 한 줄 명령에서는 영영 안 먹는다.

**해결:** ROS 블록을 `.bashrc` **맨 앞**(가드보다 위)으로 옮겼다.

```bash
# ── ROS 2 Humble 환경 ───────────────────────────────
source /opt/ros/humble/setup.bash

# 워크스페이스 오버레이 — 아직 빌드 전이면 조용히 건너뛴다
if [ -f "$HOME/mobile_robot_proto_type/install/setup.bash" ]; then
  source "$HOME/mobile_robot_proto_type/install/setup.bash"
fi

export ROS_DOMAIN_ID=0        # PC 쪽과 반드시 같아야 토픽이 보인다
export ROS_LOCALHOST_ONLY=0   # 0 이어야 원격에서 토픽이 보인다
```

백업: `~/.bashrc.bak.20260906`

> **주의 — 맨 앞에 둘 때 지켜야 할 규칙: 아무것도 출력하면 안 된다.**
> 비대화형 셸은 `scp`/`sftp` 도 쓴다. 여기서 한 글자라도 출력되면 **scp 가 깨진다.**
> `setup.bash` 는 조용해서 문제없다. 확인도 했다:
> ```bash
> $ scp -o BatchMode=yes /tmp/scptest.txt robot:/tmp/scptest.txt
> scp 업로드 OK
> ```
> 나중에 이 블록에 `echo` 를 추가하고 싶어지면 참으라는 뜻이다.

## 4. 패키징 버그 2건 (rosdep / ros2 run 을 막고 있던 것)

### 4-1. `package.xml` 의 `<buildtool_depend>ament_python</buildtool_depend>`

`rosdep check` 가 여기서 멈췄다.

```
ERROR[ebimu_pkg]: Cannot locate rosdep definition for [ament_python]
ERROR[mpc_tubempc_bridge]: Cannot locate rosdep definition for [ament_python]
```

**`ament_python` 이라는 rosdep 키는 존재하지 않는다.** 파이썬 패키지의 빌드 타입은
`<export>` 안에서 선언하는 것이고, 의존성으로 적는 게 아니다. 두 줄이 다 있었다:

```xml
<buildtool_depend>ament_python</buildtool_depend>   <!-- ← 틀렸다. 삭제 -->
...
<export>
  <build_type>ament_python</build_type>             <!-- ← 이게 맞는 선언 -->
</export>
```

패키지 5개(`ebimu_pkg`, `gui_py`, `mpc_tubempc_bridge`, `relayrobot_description`,
`relayrobot_driver`)에서 첫 줄을 지웠다. 이후:

```
$ rosdep check --from-paths src --ignore-src -r
All system dependencies have been satisfied
```

> `colcon build` 는 rosdep 을 안 쓰기 때문에 **빌드는 그냥 됐었다.** 그래서 여태
> 안 드러난 것이다. 새 PC·새 젯슨에 세팅할 때만 터지는 종류의 버그다.

### 4-2. `mpc_tubempc_bridge` 에 `setup.cfg` 누락

빌드는 성공하는데 `ros2 pkg executables mpc_tubempc_bridge` 가 **아무것도 안 뱉었다.**
`setup.py` 의 `entry_points` 는 멀쩡했는데도.

빌드 로그를 보니:

```
Installing mpc_tubempc_bridge script to .../install/mpc_tubempc_bridge/bin
```

**`bin/` 에 깔렸다.** ROS 2 는 `lib/<패키지명>/` 만 본다. 그래서 못 찾은 것이다.

원인은 `setup.cfg` 부재였다. 다른 5개 패키지엔 다 있는데 이것만 없었다:

```ini
[develop]
script_dir=$base/lib/mpc_tubempc_bridge
[install]
install_scripts=$base/lib/mpc_tubempc_bridge
```

이 파일이 콘솔 스크립트 설치 위치를 `lib/<패키지>/` 로 돌려놓는다. 만들어 넣고 재빌드하니:

```
$ ros2 pkg executables mpc_tubempc_bridge
mpc_tubempc_bridge mpc_tubempc_bridge
mpc_tubempc_bridge mpc_tubempc_path_planner
```

> **증상으로 기억할 것: "빌드는 되는데 `ros2 run` 이 패키지를 못 찾는다" → `setup.cfg` 부터 본다.**
> `ros2 pkg create` 가 자동 생성해주는 파일이라, 손으로 만든 패키지에서만 빠진다.

## 6. 원격 운용 준비 (`setup_remote_ops.sh`)

실행했다. 설치된 것:

| 항목 | 경로 |
|---|---|
| udev 규칙 | `/etc/udev/rules.d/99-robot-devices.rules` |
| 무비밀번호 종료 권한 | `/etc/sudoers.d/010-robot-poweroff` |
| 안전 종료 명령 | `/usr/local/bin/robot-off` |

SD 카드(`/dev/mmcblk0p1`, ext4) 저널 활성 / 상태 clean 확인.

### sudo 티켓 함정 — 이 스크립트는 `ssh robot '...'` 로 못 돌린다

처음에 이렇게 했더니 실패했다:

```bash
ssh robot 'echo "1234" | sudo -S -v && ./scripts/setup_remote_ops.sh'
#   → sudo 인증 OK
#   → ==> sudo 권한 확인 ... sudo: a password is required   ← 스크립트 안에서 또 물어봄
```

**원인:** tty 가 없으면 sudo 티켓이 **부모 프로세스 ID(ppid) 기준**으로 잡힌다.
바깥 셸에서 인증해도 스크립트는 다른 프로세스라 티켓을 물려받지 못한다.
(같은 셸에서 이어 실행하는 `sudo -n apt-get` 은 되는데 스크립트는 안 되는 이유가 이것이다.)

**해결 — pty 를 강제로 붙인다 (`ssh -tt`):**

```bash
printf '1234\n' | ssh -tt robot 'cd ~/mobile_robot_proto_type && ./scripts/setup_remote_ops.sh'
```

> 앞으로도 **젯슨에서 sudo 를 쓰는 스크립트를 원격 실행할 땐 `ssh -tt`** 를 쓴다.
> 출력에 `\r` 이 섞이므로 읽기 힘들면 `| tr -d '\r'` 를 붙인다.

### 안전 종료 — `robot-off` 를 파일로 분리하고 버그 2개 고쳤다

설치 직후 실제로 써보기 전에 점검하다 문제가 나왔다.

**문제 1 — 종료 대상 노드 목록이 낡아 있었다.** 하드코딩된 5개 패턴
(`real_robot_driver ebimu_publisher sllidar_node ekf_node cartographer`)으로는
**`main_driver` / `odom_sub` / `mpc_*` / `hw_test` 를 못 죽인다.**
모터를 직접 다루는 `main_driver` 가 빠진 게 특히 나쁘다 — 모터가 도는 채로
전원이 끊길 수 있었다는 뜻이다.

이름을 나열하는 방식 자체가 패키지가 늘 때마다 낡는다. 그래서 **경로로 잡는다:**

```bash
WS_PATTERN="$WS/install/[^ ]*/lib/"
```

노드 실행파일은 반드시 `install/<패키지>/lib/<패키지>/<이름>` 에 있으므로,
이 패턴 하나면 워크스페이스의 모든 노드가 걸린다. **새 노드를 추가해도
이 스크립트는 고칠 필요가 없다.** 워크스페이스 밖(apt)에서 오는
`robot_state_publisher` / `ekf_node` / `cartographer` 만 따로 나열한다.

> ⚠️ 처음엔 `$WS/install/` 로만 잡았는데, **명령줄에 그 경로 문자열이 들어 있기만 해도**
> `pkill -f` 에 걸린다. 검증 중에 실제로 내 ssh 셸이 함께 죽었다. `/lib/` 를 요구하도록
> 좁혀서 해결했다. `pkill -f` 를 쓸 땐 항상 이걸 조심할 것.

**문제 2 — 저장소에 파일이 없었다.** `setup_remote_ops.sh` 안 heredoc 으로만 존재해서
내용을 보려면 설치 스크립트를 열어야 했고 diff 도 안 잡혔다. `scripts/robot-off.sh` 로
분리하고, 설치 스크립트가 그 파일을 복사해 가도록 바꿨다.
(설치할 때 항상 `tr -d` 로 LF 정규화한다. 윈도우 PC 를 거쳐 CRLF 로 체크아웃되면
셰뱅이 깨져서 **정작 끌 때 실행이 안 된다.**)

**PC 쪽 `scripts/robot-off.ps1` 도 새로 만들었다.** 끄기 전에 IP 를 먼저 확보하고
(끄고 나면 물어볼 수 없다), ping 이 연속 3회 끊길 때까지 감시한 뒤 20초 더 기다리고
"이제 뽑아도 된다" 를 알린다. 90초 안에 안 꺼지면 경고하고 멈춘다.

```powershell
.\scripts\robot-off.ps1        # PC 에서. ping 대기까지 자동
```

**검증 (전원은 안 끄고):** `poweroff` 줄만 `echo` 로 바꾼 dry-run 으로 확인했다.
노드 2개를 띄워놓고 돌리니 둘 다 TERM 으로 정리됐고, 경로를 명령줄에 갖고 있던
테스트 셸은 살아남았다. **실제 전원 차단은 아직 안 해봤다.**

### 등록된 USB 별명 — 꽂기 전에 미리 잡아둔 것

```
모터   1a86:55d3                  ->  /dev/motor
라이다 10c4:ea60 (CP2102N)        ->  /dev/rplidar
IMU    10c4:ea60 (CP2102)         ->  /dev/ttyimu
```

이제 **꽂는 순서와 무관하게** 위 이름으로 잡힌다. `ttyUSB0/1/2` 가 순서마다 바뀌던 문제가
사라진다. 코드에서도 `/dev/ttyUSB*` 가 아니라 이 이름을 쓸 것.

### 6-1. 라이다는 A1 이 아니다 — S2 계열이다

`sllidar_a1_launch.py` 로 띄웠더니 죽었다:

```
[sllidar_node]: Error, operation time out. SL_RESULT_OPERATION_TIMEOUT!
process has died [exit code 255]
```

포트는 맞았다(`/dev/rplidar` → CP2102N). **보드레이트가 문제였다.**
직접 프로토콜을 찔러서(`0xA5 0x50` = GET_INFO) 찾았다:

```
   115200 : 무응답
   256000 : 무응답
   460800 : 무응답
  1000000 : 응답함!  model=0x81  펌웨어=1.2  하드웨어=18
```

**1,000,000 보드.** launch 파일 중 이 값을 쓰는 건 `s2` / `s3` 뿐이고,
`sllidar_s2_launch.py`(scan_mode `DenseBoost`)로 붙였더니 바로 붙었다.
`range_max` 가 **40 m** 로 보고되는 걸 보면 S3 일 가능성도 있다. 모델명 확정은 아직이다.

> `Relay_Robot_Hardware.md` 에 "RPLidar A1/A2 계열" 이라고 적혀 있던 건 **틀렸다.** 정정했다.

**함정 하나 더:** `sllidar_*_launch.py` 들의 `serial_port` 기본값이 `/dev/ttyUSB0` 인데,
지금 그건 **IMU** 다. 포트를 안 넘기면 라이다가 IMU 를 열려고 든다.
메인 launch(`real_robot_260519.launch.py`)는 `/dev/rplidar` + `1000000` + `DenseBoost` 로
**이미 올바르게** 돼 있다 — 단독 실행할 때만 조심하면 된다.

### 6-2. 모터 드라이버가 두 벌이고, 상수가 서로 다르다

| | `relayrobot_description` / `real_robot_driver_260519` | `relayrobot_driver` / `main_driver` |
|---|---|---|
| 파일 | `real_robot_driver_260519.py` | `motor_node_1.py` |

| 메인 launch 가 쓰는가 | **예** | 아니오 |

`main_driver` 쪽은 **2026-08-22 / 09-03 의 확정 결과가 반영되지 않은 낡은 사본**이다.

TF 트리가 두 값 사이에서 튀고, 원인 찾기가 매우 어려운 종류의 버그다.

## 7.5 데이터를 어떻게 보는가 — 방법 3가지

센서가 젯슨에서 돌고 있을 때, 그 데이터를 **어디서 어떻게 받아보느냐**는 세 갈래다.
쓰임이 다르니 상황에 맞게 고르면 된다.

| 방법 | 준비물 | 쓸모 |
|---|---|---|
| A. ssh + `ros2 topic` | **없음 (지금 바로 됨)** | 값 확인, 디버깅 |
| B. 구독 노드 작성 | 코드 몇 줄 | 값을 가공·기록·판단에 쓸 때 |
| C. 같은 대역 DDS | PC 에 ROS 2 Humble | **rviz 시각화** |

### A. ssh 로 바로 보기 — 준비물 없음

```bash
ssh robot 'ros2 topic list'
ssh robot 'ros2 topic hz /scan'                  # 발행 주기
ssh robot 'ros2 topic echo /ebimu_data --once'   # 값 1개만
ssh robot 'ros2 topic info /scan --verbose'      # 타입·QoS·발행자
```

`--once` 를 빼면 계속 흘러서 안 끝난다. 원격에서는 `timeout` 을 씌우는 게 편하다:

```bash
ssh robot 'timeout 5 ros2 topic echo /scan --field ranges'
```

> `.bashrc` 를 손봐놔서(2절) `ssh robot '<명령>'` 안에서 `ros2` 가 바로 잡힌다.
> `source` 를 따로 안 해도 된다.

### B. 구독 노드 직접 만들기

토픽 값을 **가공하거나 판단에 쓰려면** 결국 노드를 만들어야 한다. 이미 예제가
저장소에 있다 — `relayrobot_driver/odom_subscriber.py` (`ros2 run relayrobot_driver odom_sub`).

최소 형태는 이렇다:

```python
import rclpy
from rclpy.node import Node
from sensor_msgs.msg import LaserScan

class ScanWatcher(Node):
    def __init__(self):
        super().__init__('scan_watcher')
        # (메시지 타입, 토픽 이름, 콜백, 큐 길이)
        self.create_subscription(LaserScan, '/scan', self.on_scan, 10)

    def on_scan(self, msg):
        # inf / nan 이 섞여 나오므로 반드시 걸러야 한다
        valid = [r for r in msg.ranges
                 if msg.range_min < r < msg.range_max]
        if valid:
            self.get_logger().info(
                f'포인트 {len(valid)}개  최소 {min(valid):.2f} m')

def main():
    rclpy.init()
    rclpy.spin(ScanWatcher())

if __name__ == '__main__':
    main()
```

> ⚠️ **`ranges` 에는 `inf` 와 `nan` 이 섞여 있다.** 측정 실패한 각도의 값이다.
> 거르지 않고 `min()` 이나 평균을 내면 결과가 통째로 망가진다. 실측에서도
> 전체 배열 중 유효한 건 2780개뿐이었다.

패키지에 노드를 추가할 때는 `setup.py` 의 `entry_points` 에 한 줄 넣고 다시 빌드한다:

```python
'scan_watcher = relayrobot_driver.scan_watcher:main',
```

> 파이썬 파일만 고칠 때는 `--symlink-install` 덕분에 재빌드가 필요 없지만,
> **`setup.py` 를 건드렸으면 반드시 `colcon build` 를 다시 해야 한다.**

### C. 같은 대역에서 DDS 로 직접 받기 — rviz 를 쓰려면 이것

ROS 2 는 중앙 서버가 없다. 같은 네트워크에 있는 노드끼리 **DDS 로 서로를 찾아낸다.**
그래서 PC 에 ROS 2 만 있으면 젯슨의 토픽이 **내 PC 토픽처럼** 보인다.

조건은 네 가지다:

| 조건 | 젯슨 현재값 | PC 도 이래야 함 |
|---|---|---|
| 같은 서브넷 | `172.30.1.45` | `172.30.1.x` |
| `ROS_DOMAIN_ID` | **0** | **0** (달라도 에러 안 나고 그냥 안 보인다) |
| `ROS_LOCALHOST_ONLY` | **0** | **0** |
| RMW | `rmw_fastrtps_cpp` (Humble 기본) | 같은 배포판 권장 |

되면 PC 에서 바로:
```bash
ros2 topic list          # 젯슨 토픽이 그냥 보인다
rviz2                    # /scan 을 Fixed Frame=lidar_v1_1 로 추가
```

**Windows 에서는** WSL2 를 쓰되 **기본 NAT 모드로는 안 된다** — 멀티캐스트 탐색이 막힌다.
`C:\Users\<사용자>\.wslconfig` 에 mirrored 모드를 켜야 한다:

```ini
[wsl2]
networkingMode=mirrored
```

> 공유기가 클라이언트 간 멀티캐스트를 차단(AP isolation)하면 그래도 안 보인다.
> 그때는 Fast DDS 에 피어를 직접 지정하는 XML 설정이 필요하다.

> **X11 포워딩으로 젯슨의 rviz 를 띄우는 건 대안이 아니다.** 무선으로는 너무 느려서
> 실사용이 안 된다. `hw_test` 같은 가벼운 GUI 에만 쓸 것.
