## 1. 모터에 명령을 어떻게 보내는가 (정본)

### 1-1. 경로

```
PC ──ssh──> 젯슨 ──USB CDC(/dev/motor, 115200)──> ESP32 보드 ──RS485──> DDSM400 ×2
                    JSON 한 줄 + '\n'              중계               id=1, id=2
```

**모터에 직접 보내는 게 아니다.** JSON 을 ESP32 가 받아서 DDSM 바이너리 패킷으로 바꿔
RS485 로 중계한다. 응답도 같은 경로로 JSON 이 되어 돌아온다.
정본 소스: `src/ddsm_example/ddsm_example/json_cmd.h`, `ddsm_example.ino`.

### 1-2. 명령 일람 (실측 확인분)

| 명령 | 형식 | 비고 |
|---|---|---|
| 구동 | `{"T":10010,"id":N,"cmd":V,"act":A}` | 속도루프에서 `cmd` 단위 = **0.1RPM**. 범위 ±2100 |
| 정지 | `{"T":10010,"id":N,"cmd":0,"act":A}` | `{"T":10000,"id":N}` 도 같은 동작(펌웨어가 `ddsm_ctrl(id,0,0)` 호출) |
| 모드 | `{"T":10012,"id":N,"mode":M}` | DDSM210 계열: **0=개루프, 2=속도루프, 3=위치루프** |
| 보드타입 | `{"T":11002,"type":210}` | ⚠️ 7절 참고 — 오늘은 효과가 관측되지 않았다 |
| 정보 | `{"T":10032,"id":N}` | **누적 회전수 `mil` 과 위치 `pos` 를 준다. 매우 유용** |
| ID 확인 | `{"T":10031}` | 버스에 모터가 **하나만** 있을 때만 유효 |
| ID 변경 | `{"T":10011,"id":N}` | 버스에 모터가 하나만 있을 때만 |
| heartbeat | `{"T":11001,"time":ms}` | 기본 `-1`(비활성). **정지 명령을 안 보내면 영원히 돈다** |

### 1-3. 응답 형식

```jsonc
// 구동/정지 명령에 대한 피드백
{"T":20010,"id":1,"typ":400,"spd":294,"crt":296,"act":10,"tep":25,"err":0}
// 정보 요청(T:10032)에 대한 응답
{"T":20011,"id":1,"typ":400,"mil":9,"pos":5425,"err":0}
// CRC 실패 — 버스 충돌을 의심하라 (1-4)
{"T":20010,"crc":0}
```

### 1-4. ★ 반이중 RS485 — 명령 사이에 간격을 둬야 한다

`ddsm_ctrl()` 은 그냥 `Serial1.write()` 를 한다. **여러 모터에 연속으로 쏘면 버스가 충돌한다.**
오늘 딜레이 없이 id1·id2 를 연달아 보냈다가 `{"T":20010,"crc":0}` 을 받고 진단을 한참 헤맸다.

`MotorDriver.drive()` 에 있는 `time.sleep(0.01)` 이 바로 이것 때문이다. **지우지 말 것.**

### 1-5. ★ `pos` 는 1회전마다 되감긴다

`pos` 는 **0~32767 = 360°**, 즉 한 바퀴다. 여러 바퀴 돌면 값이 되감겨서
"안 움직였다" 로 오판하기 딱 좋다. 오늘 실제로 그렇게 오판했다.

**누적 회전량은 반드시 이렇게 구한다:**

```python
total_ticks = mil * 32768 + pos      # mil = 누적 회전수(랩)
revs = total_ticks / 32768.0
```

근거: `src/ddsm_example/ddsm_python/test_encoder.py` 주석의 `laps*32768 + raw_pos`.

## 2. 최소 동작 예시

```bash
# 젯슨에서. 오른쪽 바퀴를 2초간 전진 방향으로 (0.1 m/s 상당)
python3 - <<'EOF'
import serial, time
s = serial.Serial('/dev/motor', 115200, timeout=0)
time.sleep(0.3)
s.write(b'{"T":10012,"id":1,"mode":2}\n'); time.sleep(0.1)
t = time.time()
while time.time() - t < 2.0:
    s.write(b'{"T":10010,"id":1,"cmd":-294,"act":10}\n')   # R 은 음수가 전진
    time.sleep(0.05)
    if s.in_waiting: print(s.read(s.in_waiting).decode(errors='replace').strip())
s.write(b'{"T":10010,"id":1,"cmd":0,"act":10}\n')          # ★ 반드시 정지
s.close()
EOF
```

> 파이썬이라면 `try/finally` 로 정지를 보장해라.

## 3. 좌우 모터 ID 와 부호 (오늘 재확인)

| ID | 위치 | 전진 부호 | 드라이버 상수 |
|---|---|---|---|
| `id=1` | **오른쪽 (R)** | **음수** | `DIR_R = -1` |
| `id=2` | **왼쪽 (L)** | **양수** | `DIR_L = +1` |

좌우 허브모터가 **거울 대칭으로 장착**돼 있어서 같은 부호를 주면 반대로 돈다.
`MotorDriver` 의 `DIR_R`/`DIR_L` 이 이 하드웨어 사정을 전부 흡수하므로,
**드라이버 밖에서는 항상 "+ = 로봇 전진"** 이다. 밖에서 부호를 다시 뒤집지 말 것.

### ID 가 보드에 제대로 저장돼 있음을 확인한 방법

`{"T":10010,"id":3,...}` 을 보내면 **응답이 0 바이트**다. `id=1`, `id=2` 는 응답한다.

이게 근거가 되는 이유: 펌웨어 `ddsm_ctrl()` 은 **ID 를 전혀 검증하지 않고** 그대로
RS485 에 실어 보낸다(`ddsm_example.ino`). 즉 무응답은 "펌웨어가 걸렀다" 가 아니라
**"그 ID 를 가진 모터가 버스에 없다"** 는 뜻이다.

> 진단할 때 이 구분이 중요하다. 처음엔 "ID 3 무응답" 을 근거로 삼으면서도
> 펌웨어가 자체 필터링하는 것일 가능성을 배제하지 않아서, 소스를 확인하고서야 확정했다.

## 6. ★ 떨림(뚝뚝 끊김)의 원인 — 저속 헌팅

**증상:** 주행 중 로봇이 뚝뚝 끊기듯 떨린다. SLAM 에 쓰면 IMU 가 튈 수준.

**측정:** 명령은 일정한데 피드백 `spd` 가 계속 널뛴다. 출발 가속 구간을 제외한
**정상상태**만 골라서 속도별로 쟀다.

| cmd | 속도 | 정상상태 변동(표준편차/평균) | spd 범위 |
|---|---|---|---|
| 147 | 0.05 m/s | **28 %** | 62 ~ 227 |
| 294 | 0.10 m/s | 9 % | 241 ~ 343 |
| 441 | 0.15 m/s | 6 % | 391 ~ 481 |
| 588 | 0.20 m/s | **2 %** | 544 ~ 590 |

**저속일수록 속도루프가 심하게 헌팅한다.** 0.05 m/s 에서는 평균 145 인데 실제로는
90~230 을 계속 왕복한다. 평균값만 보면 명령과 정확히 일치해서 문제가 안 보인다.

### 결론 — 순항 속도를 0.15 m/s 이상으로 잡아라

0.20 m/s 면 변동이 2% 까지 떨어진다. 12V 에서 최고속도가 약 0.65 m/s 이므로 여유 안이다.

### 배제된 가설 (다시 시도하지 말 것)

| 가설 | 시험 | 결과 |
|---|---|---|
| `act`(가속 파라미터)가 원인 | `act` 0·1·2·5·10·20·50·100 스윕 | **전부 변동 34~65%. 차이 없음** |
| 재전송 주기가 원인 | 0.02·0.05·0.1·0.2 s 스윕 | **유의미한 차이 없음** |
| 출발 가속 구간 때문에 커 보이는 것 | 정상상태만 분리 측정 | **아니다. 정상상태에서도 31~35%** |

> ⚠️ 6절 속도별 표는 **오른쪽(id1) 데이터**다. 측정 스크립트가 id2 명령 뒤에만
> 수신 버퍼를 파싱해서 왼쪽 샘플을 놓쳤다. 다만 별도 주행 시험에서 좌우가
> L 31% / R 35% 로 거의 같았으므로 왼쪽도 같은 경향으로 본다. **왼쪽 확인은 미완.**

## 7. ⚠️ `{"T":11002,"type":210}` — 08-22 로그와 어긋나는 관측

**08-22 로그의 주장:** `type:210` 을 안 보내면 보드가 DDSM115 로 동작해서
구동 명령에 **응답조차 하지 않는다.** 전원 사이클당 1회 필수.

**오늘 관측:**

1. `{"T":11002,"type":210}` 에 **`DDSM210` 에코가 한 번도 안 왔다.**
   펌웨어 `set_ddsm_type()` 은 성공 시 `Serial.println("DDSM210")` 을 한다.
2. `type:210` 과 `type:115` 를 각각 설정하고 cmd 를 40·100·500·1000 으로 스윕했는데
   **두 경우의 결과가 사실상 동일**했다(양쪽 다 전 구간 정상 회전).
3. 타입 설정이 **no-op 인 구버전** `ddsm_python/motor_drive.py`(`{"T":11002,"id":N}` 을 보냄)
   로도 모터가 잘 돌았다.

**해석은 보류한다.** 가능성은 (a) 실제 보드 펌웨어가 저장소 소스와 다르다,
(b) 타입이 NVS 에 이미 저장돼 있어 재설정이 불필요하다, (c) 08-22 의 인과 판단이
다른 요인과 뒤섞였다 — 셋 다 검증 안 됨.

**당장의 실무 지침:** `type:210` 을 보내는 것 자체는 해롭지 않으니 초기화에 남겨둔다.
다만 **"모터가 안 돌 때 type 부터 의심하라" 는 08-22 의 조언은 오늘 근거를 잃었다.**

## 8. ⚠️ 미해결 — 세션 초반의 무토크 상태

**증상:** 세션 시작 후 한동안, 보드는 응답하는데 모터에 토크가 전혀 없었다.

- `{"T":20010,...,"spd":0,"crt":4,"tep":25,"err":0}` — 응답은 정상적으로 온다
- `spd` 가 **계속 0**, `crt` 는 0 중심 노이즈(DC 성분 없음)
- 누적 위치 변화 0
- **속도루프(mode 2) 와 개루프(mode 0) 둘 다** 무반응
- `motor_test0822.py` 가 30초 캡에 걸리고 odom −0.1 cm

**푼 방법:** 구버전 `ddsm_python/motor_drive.py` 를 그대로 import 해서 돌렸더니 움직였고,
**그 뒤로는 모든 방식에서 정상 동작**했다.

**그런데 원인은 모른다.** 당시 보드 타입은 이미 210 이었으므로(구버전 실행 직전에
`{"T":11002,"type":210}` 을 보낸 상태였다) 타입 차이로는 설명되지 않는다.
구버전과 신버전의 실질 차이는 cmd 크기(±40 vs ±294)와 부호뿐인데, 복구 후에는
cmd 500·1000 도 문제없이 돌았다.

**재발하면 확인할 것:**
1. `{"T":10032,"id":N}` 으로 `pos` 가 정말 안 변하는지 (되감김 오판 배제 — 1-5절)
2. 개루프(mode 0)에서도 전류(`crt`)에 DC 성분이 없는지
3. 모터 전원을 한 번 껐다 켠 뒤 재시도
4. 그래도 안 되면 구버전 `motor_drive.py` 로 한 번 돌려보고, **되면 그 전후 차이를 기록**

## 9. 전원 끄는 순서

**젯슨 먼저, 모터 나중.** 이유가 있다.

```bash
ssh robot robot-off        # 모터정지 → 노드종료 → sync → poweroff
# 핑이 끊기고 20초 대기, LED·팬 정지 확인
# 그 다음 12V 모터 전원 차단
```

- 젯슨은 **SD 카드 부팅**이라 라이브 차단은 카드 손상이다. 반드시 `robot-off`.
  (`sudo` 는 `poweroff`/`reboot`/`shutdown` 에 한해 NOPASSWD 로 등록돼 있다)
- 모터는 소프트웨어 종료 절차가 **없다.** 12V 전원을 그냥 끄면 된다.
- **순서가 중요한 이유:** heartbeat 가 비활성이라, 모터가 도는 상태에서 젯슨을 먼저 끄면
  **정지 명령을 보낼 수단이 사라진 채 로봇이 계속 굴러간다.**
  `robot-off` 1단계가 `/cmd_vel = 0` 을 보내는 게 이것 때문이다.

## 10. 오늘 밟은 함정

### 10-1. `pos` 되감김을 모르고 "안 움직였다" 로 오판

`cmd 294` 시험에서 `spd` 가 298·314 까지 올라갔는데 `pos` 변화는 1.4° 였다.
2바퀴를 돌아 제자리 근처로 되감긴 것인데 "안 움직임" 으로 판정했다.
→ 해결: `mil * 32768 + pos` (1-5절)

### 10-2. 버스 충돌을 자초하고 진단을 헤맴

id1·id2 명령을 딜레이 없이 연달아 보내서 `{"T":20010,"crc":0}` 이 나왔다.
반이중 RS485 라는 걸 놓쳤다. → 1-4절

### 10-3. 젯슨은 Python **3.10** 이다

f-string 안에 같은 따옴표를 중첩하거나 백슬래시를 쓰는 건 **3.12+ 문법**이다(PEP 701).
PC(3.12)에서 `ast.parse` 가 통과해도 젯슨에서 `SyntaxError` 로 죽는다.
→ 원격 실행 스크립트는 **젯슨에서** 문법 검사를 하고 보낼 것:

```bash
ssh robot 'python3 -c "import ast; ast.parse(open(\"/tmp/x.py\").read()); print(\"OK\")"'
```

### 10-4. 부팅 직후 USB 열거가 늦다

부팅 1분 시점에 `/dev/ttyACM*` 가 없어서 "모터 미연결" 로 판단했는데,
잠시 후 `/dev/motor` 까지 정상으로 잡혔다. **부팅 직후 장치 목록을 믿지 말 것.**

### 10-5. 근거 없는 전원 가설로 시간을 씀

"응답은 오는데 토크가 없다" 에서 **12V 저전압 락아웃(UVLO)** 을 유력 원인으로 지목했다.
09-13 문서가 "12V 동작은 데이터시트 계산" 이라고만 돼 있어서 미검증이라 본 것인데,
**실제로는 12V 로 잘 돈다.** 문서에 없다고 해서 안 된다는 뜻이 아니다.
