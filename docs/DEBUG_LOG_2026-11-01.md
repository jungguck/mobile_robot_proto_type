## 1. 왜 이걸 했나

9/16 이후 46일 만에 복귀. 장치를 확인해 보니 USB 가 하나도 안 꽂혀 있었고,
IMU 는 설치하지 않기로 결정했다. 그래서 "IMU 없이 SLAM 이 되나" 를 먼저 따졌다.

## 2. 핵심 발견 — IMU 는 SLAM 의 전제가 아니었다. EKF 가 문제였다

소비자가 두 군데인데 결론이 정반대였다.

| 소비자 | IMU 를 쓰나 | 결론 |
|---|---|---|
| Cartographer | `TRAJECTORY_BUILDER_2D.use_imu_data = false` | **원래부터 안 쓴다.** 손댈 것 없음 |
| EKF (`ekf.yaml`) | yaw 소스를 **IMU 하나로 통일** | **이게 블로커였다** |

옛 `ekf.yaml` 은 08-22 에 "바퀴 yaw 와 IMU yaw 가 서로 밀고 당긴다" 는 이유로
바퀴의 x·y·yaw·v_yaw 를 **전부 false** 로 끄고 vx·vy 만 받았다. 방향은 IMU 전담.
→ **IMU 를 빼면 yaw 관측이 0 개**가 되어 로봇이 제자리 회전을 해도 EKF 는 계속
정면을 본다고 믿는다. 그 `/odom` 이 SLAM prior 로 들어가면 지도가 깨진다
(README: yaw 오차는 scan 매칭이 가장 못 버티는 종류).

**해법은 최소였다.** 바퀴의 x·y·yaw·v_yaw 를 **다시 켜는 것.**
끈 이유가 "IMU 와의 충돌" 이었으므로, IMU 가 없으면 끌 이유도 없어진다.

## 3. EKF 를 아예 빼지 못한 이유 (중요 — 다시 헷갈리지 말 것)

`odom→base_link` TF 를 발행하는 노드가 **EKF 뿐**이다.
`real_robot_driver_260519.py` 는 `TransformBroadcaster` 를 **import 만 하고
실제로 안 쓴다** — 이중 발행을 막으려고 일부러 그렇게 뒀다 (코드 주석에 명시됨).
→ EKF 를 빼면 TF 사슬이 끊겨 Cartographer 가 아예 못 돈다.
센서가 하나뿐이라 "융합" 은 없고 사실상 패스스루 + 평활화지만, **노드는 남겨야 한다.**
