**주제:** DDSM400 모터 구동 실패 원인 규명 + 통신 규약 확정 + IMU 무발행 문제 + 오도메트리 직진 측정

진짜 원인을 찾았다. 그 과정에서 명령 단위·부호·ID 매핑까지 전부 실측으로 확정했다.

## 0. 한 줄 요약 (다음에 이것만 기억하면 됨)

- 모터 초기화는 **`{"T":11002,"type":210}`**. `id` 가 아니라 **`type`** 이고, **전원 사이클당 1회** 필요.
  이걸 빼먹으면 보드가 구동 명령에 **응답조차 안 한다.**
- `cmd` / `spd` 단위는 RPM 이 아니라 **0.1RPM**. (cmd 100 = 10 RPM)
- **id=1 → 오른쪽**, **id=2 → 왼쪽**.
- 전진 부호는 **R = 음수, L = 양수**.
- 이 보드는 **명령을 받을 때만** 피드백을 보낸다. 주기적으로 안 보내면 `read_feedback()` 이
  **옛 값을 그대로 돌려주고**, 그게 계속 적분되어 거리가 부풀려진다.
- 보드 heartbeat 는 기본 **비활성(-1)**. 정지 명령 없이 노드가 죽으면 **로봇이 계속 굴러간다.**

## 1. 겪은 문제와 원인

### 1-1. 모터가 안 돎 — 통신은 되는데 구동 명령만 무시
- **증상:** 포트는 열리고, `{"T":10012,...,"mode":2}`(모드 변경)에는 hex 프레임
  `0x01, 0xA0, 0x02, ...` 로 응답이 온다. 그런데 `{"T":10010,...}`(구동)에는
  **아무 응답도 없고 바퀴도 안 돈다.**
- **원인:** 보드 타입이 DDSM115(기본값)로 잡혀 있었다. DDSM400 은 **DDSM210 계열 프로토콜**을 쓴다.
  타입이 틀리면 구동 명령 자체가 처리되지 않는다.
- **왜 못 찾았나:** 기존 `motor_drive_1.py` 가 `{"T":11002,"id":N}` 을 보내고 있었다.
  `T:11002`(CMD_TYPE)는 **`id` 가 아니라 `type` 을 받는 명령**인데, 필드 이름이 틀려서
  아무 효과가 없었다. 에러도 안 난다 — 조용히 무시된다.
- **확정 근거:** `src/ddsm_example/ddsm_example/ddsm_example.ino` 의 `set_ddsm_type()` 은
  `115` 와 `210` 만 처리한다. 그 외 값(예: `400`)은 **조용히 무시**된다.
  ```c
  void set_ddsm_type(int inputType) {
    if (inputType == 115)      { ddsm_type = TYPE_DDSM115; ... }
    else if (inputType == 210) { ddsm_type = TYPE_DDSM210; ... }
  }   // 그 외는 아무것도 안 함
  ```
- **함정:** 모터 피드백은 `"typ":400` 이라고 알려준다. 그래서 `type:400` 을 보내고 싶어지는데,
  펌웨어가 받지 않는다. 그런데 **직전에 210 을 설정해 뒀으면 그대로 잘 동작**하기 때문에
  "400 도 되는구나" 라고 착각하기 딱 좋다. 실제로 한 번 속았다.

### 1-2. 명령 속도가 실제의 1/10
- **증상:** `cmd_vel` 로 0.2 m/s 를 줘도 로봇이 기어간다.
- **원인:** `calculate_rpms()` 가 `cmd` 를 RPM 으로 보고 `×60` 을 곱했다.
  실제 단위는 **0.1RPM** 이라 `×600` 이 맞다.
- **확정 근거:** `cmd:100` 을 보내면 `spd:105` 가 회신된다. cmd 와 spd 는 같은 단위이고,
  둘 다 실제 RPM 의 10배다. (DDSM210 계열 규약)
- **주의:** 오도메트리 쪽 `/600.0` 은 **원래부터 맞았다.** 명령 쪽만 틀려 있어서
  "명령과 계측이 10배 어긋나는" 비대칭 상태였다.

### 1-3. 전진 명령에 로봇이 후진
- **원인:** 좌우 허브모터가 거울 대칭으로 장착돼 있어 같은 부호를 주면 반대로 돈다.
  기존 규약 `R=+, L=-` 는 실제로는 **후진**이었다.
- **해결:** `MotorDriver` 에 `DIR_R = -1`, `DIR_L = +1` 상수를 두고
  `drive()` 와 `read_feedback()` **양쪽에 똑같이 적용**했다.
  이제 드라이버 밖에서는 항상 **"+ = 로봇 전진"** 이다.
- **부수 효과:** 이 변경으로 `real_robot_driver_260519.py` 의 `rpm_L = -rpm_L` 은
  **중복 반전이 되어 제거**했다. → 아래 3번 항목 참고.

### 1-4. 정지했는데 오도메트리가 계속 늘어남 (유령 거리)
- **증상:** 50cm 목표 주행에서 정지 명령 시점 odom 은 50.4cm 인데,
  1초 더 지켜보니 **59.8cm** 로 늘어나 있었다. 로봇은 이미 멈춰 있었다.
- **원인:** `MotorDriver.read_feedback()` 은 새 프레임이 없으면 **직전 rpm 값을 그대로 반환**한다.
  그런데 이 보드는 **명령을 받았을 때만** 피드백을 보낸다.
  정지 명령을 한 번만 보내고 가만히 있으면 → 새 피드백 없음 → 옛 속도가 계속 적분된다.
- **해결(테스트 스크립트):** 정지 구간에서도 정지 명령을 **계속 재전송**해서 피드백을 살려둔다.
  이렇게 하니 관성 주행분이 **9.4cm → 2.1cm**, 정지 후 잔여 속도 **0.0 cm/s** 로 정상화됐다.
- **아직 안 고친 곳:** `real_robot_driver_260519.py` 의 `timer_callback()` 은
  피드백만 읽고 명령을 재전송하지 않는다. `cmd_vel` 이 끊기면 **로봇은 서 있는데 odom 은 계속 전진**한다.

### 1-5. `/ebimu_data` 가 한 번도 발행되지 않음
- **증상:** IMU 노드는 뜨고 "Calibration done" 도 찍히는데, 토픽에 메시지가 없다.
- **원인 1:** 이 센서는 현재 **3개 필드만** 출력한다. → `*-5.82,-2.39,135.80` (roll, pitch, yaw)
  그런데 `_read_line()` 이 `len(words) != 9` 면 전부 버렸다. **모든 줄이 버려졌다.**
- **원인 2:** `timer_callback()` 이 `d[3]`~`d[8]` 을 무조건 참조해서 `IndexError` 가 나는데,
  `except Exception: pass` 가 조용히 삼켰다. **에러 로그조차 안 남는다.**
- **해결:** 3개 포맷을 받아들이고, 가속도/자이로는 `covariance[0] = -1`(ROS 규약: 미제공)로 표시.
  `except` 절에 경고 로그 추가. 자세만 나오는 센서면 10초 바이어스 캘리브레이션도 건너뛴다.
- **확인:** `/ebimu_data` 발행됨. 쿼터니언 → yaw 135.3° 로 raw 값 135.80 과 일치.

## 2. 왜 헷갈렸나 (진짜 교훈)

- **필드 이름이 틀려도 에러가 안 난다.** `{"T":11002,"id":2}` 는 문법적으로 멀쩡한 JSON 이고
  보드도 받아들인다. 다만 아무 일도 안 일어날 뿐이다. 펌웨어 소스(`json_cmd.h`,
  `ddsm_example.ino`)를 직접 열어보기 전에는 알 수 없었다.
  → **프로토콜이 의심되면 문서가 아니라 펌웨어 소스를 봐라.** 이 저장소에 `src/ddsm_example/` 로 들어 있다.

- **설정이 전원 사이클 동안 유지된다.** 한 번 `type:210` 을 넣어두면 그 뒤 실행되는
  모든 스크립트가 잘 동작한다. 그래서 "이 스크립트는 되고 저건 안 되네" 가 아니라
  **"내가 아까 뭘 보냈는지" 가 결과를 좌우한다.** 재현 테스트는 보드 전원을 껐다 켜고 해야 정확하다.

- **`except Exception: pass` 는 디버깅을 불가능하게 만든다.** IMU 가 안 나오는 이유를
  코드만 봐서는 알 수 없었다. 로그가 하나도 안 남기 때문이다.

- **stale 값을 반환하는 getter 는 위험하다.** `read_feedback()` 이 "최신 값"을 주는 것처럼
  보이지만 실제로는 "마지막으로 본 값"이다. 이걸 적분에 쓰면 조용히 틀린 결과가 나온다.

- **`raw 데이터가 안 온다` 와 `장치가 안 붙어 있다` 는 다르다.**
  이번에도 "포트가 비어 있다"(= 다른 프로세스가 점유 안 함)를 "장치 미연결"로 오해하는 일이 있었다.

> ⚠️ **2026-09-03 갱신: 아래 1번은 종결됐다.**

3. **heartbeat 워치독 설정.** `{"T":11001,"time":500}` 을 초기화에 넣을지 검토.

4. **IMU + 바퀴 융합 직진 테스트 미실시.**

## 7. EKF 융합 전략 변경

`config/ekf.yaml` 을 다음과 같이 바꿨다.

- **방향(yaw)**: IMU 절대 yaw 만 사용
- **위치(x, y)**: 바퀴 속도 `vx` 를 그 yaw 방향으로 적분

**왜 바퀴의 절대 x, y 를 안 쓰나:**
`/odom_raw` 의 x, y 는 "바퀴가 **자기 yaw 로** 적분한" 위치다.
바퀴 yaw 와 IMU yaw 가 어긋나면 두 값이 서로 밀고 당겨서 **직진 중에도 궤적이 좌우로 흔들린다.**
속도만 넘기고 방향은 IMU 에 맡기면 이 충돌이 사라진다.

**왜 `v_yaw` 를 양쪽 다 껐나:**
이 IMU 는 현재 자세만 출력하고 **자이로 값을 안 준다.**
바퀴 `v_yaw` 는 좌우 rpm 차이로 계산한 값이라 IMU yaw 와 경쟁하게 되므로,
방향 소스를 IMU 하나로 통일했다.

1. 장치 확인 → `./check_devices.sh`
2. 모터가 안 돌면 → **먼저 `{"T":11002,"type":210}` 을 보냈는지 확인.**
   보드 전원을 껐다 켰으면 다시 보내야 한다.
3. 프로토콜이 의심되면 → `src/ddsm_example/ddsm_example/json_cmd.h` 와
   `ddsm_example.ino` 를 열어봐라. 문서보다 소스가 정확하다.
4. 모터 응답 확인은 패키지 원본 스크립트로 →
   `python3 src/ddsm_example/ddsm_python/simply.py /dev/motor`
   ⚠️ `check_feedback.py` 는 포트가 `/dev/ttyUSB0`(= IMU) 로 하드코딩돼 있으니 그대로 쓰지 말 것.
5. 토픽이 안 나오면 → 노드 로그부터 봐라. `except: pass` 로 삼켜지고 있을 수 있다.
6. `ros2 topic hz` 를 파이프로 연결하면 출력이 버퍼링돼서 `timeout` 에 죽을 때 아무것도 안 남는다.
   `ros2 topic echo` 를 써라. (`--once` 는 Foxy 에 없는 옵션이다)
