# 🛠️ Debugging Experience

프로젝트 개발 과정에서 발생한 주요 문제들과 해결책을 집대성합니다. 이 기록은 향후 유사한 문제 발생 시 가이드라인이 됩니다.

## 1. TF 충돌 (Double TF Issue)
- **현상**: RViz에서 로봇이 비정상적으로 떨리며 SLAM이 경로를 소실함.
- **원인**: 모터 드라이버 노드와 EKF 노드가 둘 다 `odom -> base_link` TF를 동시에 발행함.
- **해결**: 드라이버의 TF 발행 기능을 끄고, 센서 데이터만 전달하도록 수정. EKF 노드만 TF를 책임지도록 단일화함.

## 2. 좀비 프로세스 (Zombie Processes)
- **현상**: GUI 종료 후에도 SLAM이나 드라이버 노드가 백그라운드에 남아 시리얼 포트를 점유함.
- **원인**: 부모 프로세스(GUI)만 죽고 자식 프로세스들이 고아가 됨.
- **해결**: Python의 `os.setsid()`를 사용해 새로운 프로세스 그룹을 생성하고, 종료 시 `os.killpg()`로 그룹 전체를 제거함.

## 3. MPC 궤적 추종 실패 (Blind Control)
- **현상**: 로봇이 목표지점과 상관없는 방향으로 움직임.
- **원인**: 제어기가 현재 로봇의 위치(`/odom`)를 피드백 받지 않고 오픈 루프로 동작함.
- **해결**: MPC 로직 내에 `/odom` 구독(Subscriber)을 추가하여 목표치와의 오차를 실시간 계산하도록 수정.

## 4. 시뮬레이션 시간 오차 (Sim Time Issue)
- **현상**: 실제 로봇 가동 시 데이터가 업데이트되지 않거나 노드가 멈춤.
- **원인**: `use_sim_time` 파라미터가 `true`로 설정되어 실제 시스템 시계를 무시함.
- **해결**: 실제 로봇 런칭 파일에서 해당 값을 반드시 `false`로 명시함.

## 5. RPM 변환 계수 오류 (Odom 속도 10배 오차)
- **현상**: `/odom_raw`의 속도가 실제보다 10배 크게 계산됨. EKF가 엉뚱한 위치를 추정하고 SLAM 지도가 왜곡됨.
- **원인**: `real_robot_driver_260519.py`에서 RPM→m/s 변환 시 `/6.0` 사용. DDSM400은 `spd` 피드백이 실제 RPM의 10배이므로 `/600.0`이 맞음. (cmd 100 → 실제 10 RPM → spd 피드백 100)
- **해결**: `vl = (rpm_L / 600.0) * (2 * math.pi * self.wheel_radius)` 로 수정.
- **파일**: `src/relayrobot_description/relayrobot_description/real_robot_driver_260519.py` line 80-81

## 6. 왼쪽 모터 피드백 부호 미반전 (Odom 방향 오류) ⚠️ 2026-08-22 무효
- **현상**: 전진 명령 시 로봇이 제자리 회전만 함. vl < 0, vr > 0 으로 선속도가 상쇄되고 각속도가 비정상적으로 큰 값.
- **원인**: 왼쪽 모터는 `drive()`에서 `-rpm_L`로 음수 명령을 보내므로 `spd` 피드백도 음수로 돌아옴. `motor_node_1.py`는 `rpm_L = -rpm_L`로 부호를 반전하는데 `real_robot_driver_260519.py`에는 이 줄이 없었음. `motor_drive_1.py` 83~84번 줄 주석에 명시되어 있었으나 구현이 누락됨.
- **해결**: `rpm_L, rpm_R = self.driver.read_feedback()` 직후에 `rpm_L = -rpm_L` 추가.
- **파일**: `src/relayrobot_description/relayrobot_description/real_robot_driver_260519.py` line 78
- **⚠️ 2026-08-22 무효화**: 부호 처리를 `MotorDriver` 안으로 옮겼다(`DIR_L`/`DIR_R`).
  이제 `read_feedback()` 이 이미 "+ = 로봇 전진" 으로 돌려주므로,
  노드에서 `rpm_L = -rpm_L` 을 다시 하면 **이중 반전**이 된다. 해당 줄은 제거됨.
  → 아래 9번 항목 참고.

## 7. 모터 무응답 — 보드 타입 미설정 (2026-08-22)
- **현상**: 시리얼은 열리고 모드 변경 명령(`T:10012`)에는 응답이 오는데, 구동 명령(`T:10010`)에는 **응답도 없고 바퀴도 안 돎**.
- **원인**: 보드가 기본값인 DDSM115 프로토콜로 동작 중이었음. DDSM400 은 **DDSM210 계열** 규약을 쓴다. 기존 코드는 `{"T":11002,"id":N}` 을 보냈는데, `T:11002`(CMD_TYPE)는 `id` 가 아니라 **`type`** 을 받는 명령이라 아무 효과가 없었다. 에러도 안 난다.
- **해결**: `{"T":11002,"type":210}` 으로 수정. **전원 사이클당 1회** 필요.
- **함정**: 피드백은 `"typ":400` 이라고 알려주지만 펌웨어(`set_ddsm_type()`)는 **115/210 만** 인정하고 그 외 값은 조용히 무시한다. 직전에 210 을 설정해 뒀다면 `type:400` 을 보내도 잘 동작하는 것처럼 보이므로 착각하기 쉽다.
- **파일**: `src/relayrobot_description/relayrobot_description/motor_drive_1.py` `initialize_motors()`

## 8. 명령 속도가 실제의 1/10 (2026-08-22)
- **현상**: `cmd_vel` 로 0.2 m/s 를 줘도 로봇이 기어감.
- **원인**: `calculate_rpms()` 가 `cmd` 를 RPM 으로 보고 `×60` 을 곱했다. 실제 단위는 **0.1RPM**.
- **확정 근거**: `cmd:100` → `spd:105` 회신. cmd 와 spd 는 같은 단위이고 둘 다 실제 RPM 의 10배.
- **해결**: `×600` 으로 수정.
- **주의**: 오도메트리 쪽 `/600.0`(5번 항목)은 **원래부터 맞았다.** 명령 쪽만 틀려서 명령과 계측이 10배 어긋난 비대칭 상태였다.
- **파일**: `src/relayrobot_description/relayrobot_description/motor_drive_1.py` `calculate_rpms()`

## 9. 전진 명령에 로봇이 후진 (2026-08-22)
- **현상**: 전진 명령(`R=+, L=-`)을 주면 로봇이 뒤로 감.
- **원인**: 좌우 허브모터가 거울 대칭으로 장착돼 있어 부호 규약이 통째로 뒤집혀 있었다.
- **해결**: `MotorDriver` 에 `DIR_R = -1`, `DIR_L = +1` 상수를 두고 `drive()` 와 `read_feedback()` **양쪽에 동일하게** 적용. 드라이버 바깥에서는 항상 "+ = 로봇 전진".
- **규칙**: **부호는 `MotorDriver` 가 전부 흡수한다. 드라이버 바깥에서 부호를 건드리지 마라.** (6번 항목이 이걸로 무효화됨)
- **덤**: 모터 ID 물리 위치 확정 — **id=1 오른쪽, id=2 왼쪽**.

## 10. 정지했는데 odom 이 계속 늘어남 — stale 피드백 (2026-08-22)
- **현상**: 50cm 주행 후 정지했는데 odom 이 계속 증가. 정지 시점 50.4cm → 1초 뒤 **59.8cm**. 로봇은 이미 멈춰 있었다.
- **원인**: `read_feedback()` 은 새 프레임이 없으면 **직전 rpm 을 그대로 반환**한다. 그런데 이 보드는 **명령을 받을 때만** 피드백을 보낸다. 정지 명령을 한 번만 보내고 가만히 있으면 옛 속도가 계속 적분된다.
- **해결(테스트)**: 정지 구간에서도 명령을 계속 재전송. 관성 주행분 **9.4cm → 2.1cm**, 잔여 속도 0.0 cm/s 로 정상화.
- **✅ 해결 (2026-09-13)**: `real_robot_driver_260519.py` 의 `timer_callback()` 이 **10Hz 로 명령을 재전송**한다. 재전송이 `drive()` 안의 `read_feedback()` 을 매 주기 돌리므로 stale 자체가 씻긴다. 더해서 `MotorDriver.feedback_age()` 가 `feedback_timeout`(0.3s)을 넘으면 **속도를 0 으로 간주**해 적분을 끊는다.
- **파일**: `motor_test0822.py` (최초 해결 예시), `real_robot_driver_260519.py` / `motor_drive_1.py` (적용 완료)
- **실기 검증 미완**: 시리얼 포트가 필요해 시뮬레이터로 대체 불가. README `STAGE 4-B` 에서 확인할 것.

## 11. `/ebimu_data` 가 한 번도 발행되지 않음 (2026-08-22)
- **현상**: IMU 노드는 정상 기동하고 "Calibration done" 도 찍히는데 토픽에 메시지가 없음.
- **원인 1**: 이 센서는 **3개 필드만** 출력한다(`*ROLL,PITCH,YAW`). `_read_line()` 이 `len(words) != 9` 면 전부 버려서 모든 줄이 폐기됐다.
- **원인 2**: `timer_callback()` 이 `d[3]`~`d[8]` 을 무조건 참조해 `IndexError` 가 났는데, `except Exception: pass` 가 조용히 삼켜 **에러 로그조차 안 남았다.**
- **해결**: 3필드 포맷 지원, 가속도/자이로는 `covariance[0] = -1`(ROS 규약: 미제공)로 표시, `except` 절에 경고 로그 추가, 자세만 나오는 센서면 10초 캘리브레이션 건너뛰기.
- **교훈**: `except Exception: pass` 는 디버깅을 불가능하게 만든다.
- **파일**: `src/ebimu_pkg/ebimu_pkg/ebimu_publisher.py`

## 12. 바퀴 odom 과 IMU yaw 를 동시에 융합하면 궤적이 흔들림 (2026-08-22)
- **원인**: `/odom_raw` 의 x, y 는 "바퀴가 **자기 yaw 로** 적분한" 위치다. 바퀴 yaw 와 IMU yaw 가 어긋나면 두 heading 이 서로 밀고 당겨 직진 중에도 궤적이 좌우로 흔들린다.
- **해결**: 방향은 IMU 절대 yaw 만, 위치는 바퀴 `vx` 를 그 yaw 방향으로 적분하도록 변경. `odom0_config` 의 x, y 를 끄고 `vx` 만 사용.
- **덤**: `v_yaw` 는 양쪽 다 끔. 이 IMU 는 자이로를 안 주고, 바퀴 `v_yaw` 는 IMU yaw 와 경쟁하므로 방향 소스를 하나로 통일했다.
- **파일**: `src/relayrobot_description/config/ekf.yaml`
- **⚠️ 미검증**: 실제 주행으로 직진성을 확인하지 못했다. 다음 세션에서 검증할 것.

## 13. Tube-MPC 의 QP 가 100% infeasible — 로봇이 제자리에서 멈춤 (2026-09-13)
- **현상**: A* 경로는 정상인데 `/mpc/status` 가 12초간 94번 **전부 `QP_FAILED`**. 로봇이 조금 가다 선다.
- **원인**: 상태 제약 `x_min` 의 heading 성분 `-0.3` 이 tube 크기만큼 타이트닝되어 실효 **0.25 rad(14°)** 가 된다. 그런데 A* 경로 추종 시 **첫 참조점의 접선 방향과 로봇의 현재 방향은 출발 시 쉽게 20~30° 벌어진다** → 첫 사이클부터 제약 위반 → 항상 infeasible.
- **측정**: 추측하지 않고 오프라인으로 재현해 경계를 쟀다. `e_theta=0.25 → OK`, `0.30 → FAIL`. **실패 경계가 정확히 타이트닝된 상한과 일치**했다.
- **해결**: `error_yaw_limit` 파라미터로 분리, 기본 `3.2`(사실상 무제한). **heading 오차는 안전 제약이 아니다** — 돌아서 줄이면 되는 값이고, 지켜야 할 것은 위치 오차(tube)다.
- **교훈**: "제약을 조금 풀어보자" 가 아니라 **실패 경계를 재서 원인을 특정**하면 왜 그 값이어야 하는지까지 설명된다.
- **파일**: `src/mpc_tubempc_bridge/src/mpc_tubempc_bridge/bridge_node.py`

## 14. 프레임을 섞어 쓰면 SLAM 이 정확해질수록 추종이 나빠진다 (2026-09-13)
- **현상**: (구조적 결함 — 실기 발현 전 코드 리뷰/시뮬레이션에서 발견)
- **원인**: `bridge_node` 는 `/odom` 의 pose(**odom 프레임**)를 현재 위치로 썼는데, `/global_path` 와 `/mpc_goal` 은 **map 프레임**이었다. 두 노드 어디에도 tf2 가 없어 **변환 없이 뺐다.** 추종오차에 `map→odom`(SLAM 드리프트 보정분)이 통째로 섞인다.
- **왜 안 들켰나**: 시작 직후에는 `map ≈ odom` 이라 **잘 되는 것처럼 보인다.** 주행할수록 나빠진다.
- **해결**: 두 노드 모두 `global_frame`(기본 `map`) → `base_link` **TF 조회**로 위치를 받는다. `global_frame:=odom` 이면 SLAM 없이도 동작.
- **검증**: `tools/mpc_sim.py` 로 `map→odom` 을 (0.5, 0.5, 0.3) 일부러 틀어놓고도 목표 도달, QP 실패 0회.
- **곁가지**: TF 조회에 `timeout` 을 주면 안 된다. `rclpy.spin()` 은 단일 스레드라 자는 동안 `/tf` 가 배달되지 않아 **기다려도 성공할 수 없고** 제어 주기만 먹는다.
- **파일**: `bridge_node.py`, `path_planner.py` / 자세히는 [[TF_Coordinate_System]]

## 15. ⚠️ 경로가 없으면 장애물로 직진했다 (2026-09-13, 코드 리뷰에서 발견)
- **현상**: (안전 결함 — 실기 투입 전 발견)
- **원인**: `use_global_path` 모드에서 `/mpc_goal` 은 즉시 반영되는데 `/global_path` 는 아직 없을 수 있다(계획기 기동 전·사망·**A\* 실패**). 그때 목표까지 **직선 참조**를 만들어 그대로 달렸다 — **지도를 전혀 안 보고.** A* 가 "경로 없음"·"목표가 막힘" 으로 실패한 상황이 곧 이 상황이라, **갈 수 없다고 판정된 목표를 향해 장애물을 뚫고 직진**하는 구조였다.
- **해결**: 경로가 없거나 `path_timeout`(2s)보다 낡으면 **정지 + `/mpc/status = NO_PATH`**. 계획기는 실패 시 **빈 경로를 발행**해 낡은 경로를 무효화한다.
- **검증**: 장애물 한가운데(1.7, 0.5)를 목표로 주니 `Goal cell is not free` → 빈 경로 → `NO_PATH`, `cmd_vel.x = 0.0`, **로봇 안 움직임.** 미탐색 구역 목표도 동일.
- **교훈**: **"값이 없을 때의 기본 동작"이 곧 안전 설계다.** 폴백이 "그래도 가 본다" 면 그건 폴백이 아니라 새 사고 경로다.
- **파일**: `bridge_node.py`, `path_planner.py`

## 16. 자율주행 모드에서는 "명령을 멈추는" 비상정지가 통하지 않는다 (2026-09-13)
- **현상**: (문서 결함 — `robot-up.sh nav` 안내문이 틀렸다)
- **원인**: teleop 에서는 `/cmd_vel` 발행을 그만두면 드라이버 watchdog 이 0.5초 뒤 세운다. 그런데 자율주행 모드는 **MPC 가 10Hz 로 계속 쏘고 있다**(정지 명령 포함). 조작자에게는 "멈출 발행" 이 없어 watchdog 이 **영원히 안 걸린다.**
- **해결**: 안내를 실제로 되는 동작으로 정정. `ssh robot 'tmux kill-window -t robot:mpc'` (MPC 만) 또는 `robot-up.sh stop` (전부). 둘 다 MPC 가 멎으므로 그제서야 watchdog 이 작동한다.
- **교훈**: 안전 절차는 **그 모드에서 실제로 되는지** 확인하고 적어야 한다. 다른 모드에서 되던 절차가 그대로 통할 거라 가정하면 안 된다.
- **파일**: `scripts/robot-up.sh`, `README.md`
