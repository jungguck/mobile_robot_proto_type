## 4. Jetson Orin Nano — JetPack 6.2.1 부팅 실패

### 증상
`jetson-orin-nano-devkit-super-SD-image_JP6.2.1` 을 SD 에 구워 부팅하면
**UEFI Interactive Shell** 로 떨어진다. (= UEFI 가 부팅 가능한 장치를 못 찾음)

### 원인
Orin Nano 개발자 키트는 **부트로더(UEFI)를 SD 가 아니라 모듈의 QSPI 플래시에 저장**한다.
SD 에는 커널과 루트파일시스템만 있다. 공장 출하 펌웨어가 35.x(JetPack 5 세대)면
**36.x 인 JetPack 6 SD 이미지를 못 읽는다.** SD 카드를 다시 굽거나 바꿔도 동일 증상.

- 확인법: 부팅 중 **ESC 연타** → UEFI 메뉴 최상단에 펌웨어 버전. `35.x` 면 확진.
- UEFI Shell 에서 `map -r` 로 `FS0:` 가 보이면 카드는 읽히는 것 → 펌웨어 문제 확정.

### 해결 — JetPack 5.1.3 을 bridge 로 (호스트 PC / 리커버리 모드 불필요)

NVIDIA 가 공식 문서화한 microSD-only 경로다. **재부팅 2회**가 필요하다.

**1) JetPack 5.1.3 SD 이미지** (L4T 35.5.0 / Ubuntu 20.04)
```
https://developer.nvidia.com/downloads/embedded/l4t/r35_release_v5.0/jp513-orin-nano-sd-card-image.zip
```
페이지: https://developer.nvidia.com/embedded/jetpack-sdk-513

> NVIDIA 가 2024-05-28 에 이미지를 교체했다(`_b29`). 그 이전 파일은 문제가 있으니 새로 받을 것.
> 64GB 이상 UHS-1 카드에 Balena Etcher 로 굽는다.

**2) 부팅 후 펌웨어 업데이트**
```bash
# 첫 부팅 → 우분투 초기 설정 + 인터넷 연결

sudo systemctl status nv-l4t-bootloader-config   # 업데이트 예약 확인
sudo reboot                                       # [재부팅 1] 펌웨어 업데이트 실행

sudo nvbootctrl dump-slots-info                   # 버전 확인

sudo apt update
sudo apt install nvidia-l4t-jetson-orin-nano-qspi-updater
sudo reboot                                       # [재부팅 2] QSPI 갱신
```

> ⚠️ **두 재부팅 모두, 펌웨어 업데이트 진행 중 전원을 절대 빼지 말 것.** 벽돌이 될 수 있다.
> **19V 정품 어댑터**를 쓸 것 (USB-C 전원은 업데이트 중 전류가 부족할 수 있음).

끝나면 펌웨어가 36.x 가 되고, 처음 구웠던 **JetPack 6.2.1 SD 카드가 그대로 부팅**된다.

### 펌웨어가 이미 36.x 인데도 안 될 때
- **NVMe SSD** 가 꽂혀 있으면 UEFI 부트 순서가 NVMe 를 먼저 시도하다 Shell 로 떨어질 수 있다.
  SSD 를 빼고 SD 만으로 부팅해보거나 Boot Manager 에서 SD 를 1순위로.
- SD 카드 불량/용량 뻥튀기. 64GB 이상 정품 A2 급 + Etcher 의 verify 통과 확인.

### JetPack 5 에 머무를지 6 으로 갈지

| | JetPack 5 (Ubuntu 20.04 / Foxy) | JetPack 6 (Ubuntu 22.04+ ) |
|---|---|---|
| 6개 패키지 빌드 | ✅ | ✅ |
| 실기 파이프라인 | ✅ | ✅ |
| **Gazebo 시뮬레이션** | ✅ | ❌ (Gazebo Classic EOL) |
| Super 모드(MAXN 성능) | ❌ | ✅ |
| ROS 배포판 지원 | Foxy — 2023-05 EOL, apt 아카이브 | 최신 |

**결론: 지금 결정하지 않아도 된다.** 위 펌웨어 업데이트 2단계까지 끝내두면
그 뒤로는 **SD 카드만 바꿔 끼워서** 5 ↔ 6 을 오갈 수 있다.
Cartographer 가 CPU 를 많이 쓰므로 Super 모드가 필요해지면 그때 6 으로 가면 된다.

## 5. 원격 접속 방침 (PC = Windows 11 → 젯슨)

| 목적 | 방법 | 젯슨 부하 |
|---|---|---|
| 명령 실행 | SSH + **tmux** | 없음 |
| 코드 편집 + 터미널 다중 | **VS Code Remote-SSH** | 중간 |
| 기존 `hw_test` GUI 띄우기 | `ssh -X` (X11 포워딩) | 낮음 |
| 지도/스캔/TF 보기 | **Foxglove Studio** | 낮음 |
| 우분투 데스크톱 전체 | NoMachine / VNC | **높음 — 비권장** |

### 채택
```
평소 작업     : VS Code Remote-SSH   (Ubuntu 20.04·22.04 모두 지원됨)
하드웨어 점검 : ssh -X  +  ros2 run gui_py hw_test
SLAM 모니터링 : Foxglove Studio + foxglove_bridge
전체 데스크톱 : 안 씀
```

### 근거
- **tmux 는 선택이 아니라 필수.** detach 해두면 무선 연결이 끊겨도 ROS 노드가 안 죽는다.
  그냥 SSH 로 띄우면 연결이 끊기는 순간 주행 중에 드라이버가 같이 죽는다.
  ```bash
  tmux new -s robot     # Ctrl-b % 좌우분할 / Ctrl-b " 상하분할 / Ctrl-b d 분리
  tmux attach -t robot
  ```
- **`hw_test` GUI 는 tkinter** 라 OpenGL 을 안 쓴다 → X11 포워딩으로 잘 넘어오고 대역폭도 적게 쓴다.
  Windows 쪽에 X 서버(VcXsrv 또는 MobaXterm)만 있으면 된다.
- **RViz2 를 젯슨에서 띄워 화면을 스트리밍하는 건 최악의 조합.**
  젯슨이 렌더링과 영상 인코딩을 둘 다 하게 되어 SLAM 에 쓸 CPU 를 뺏긴다.
  대신 젯슨은 데이터만 보내고 PC 가 그린다:
  ```bash
  sudo apt install ros-$ROS_DISTRO-foxglove-bridge
  ros2 launch foxglove_bridge foxglove_bridge_launch.xml
  ```
  Windows 에서 Foxglove Studio → `ws://<젯슨IP>:8765`. **Windows 에 ROS 설치 불필요.**
- **NoMachine/VNC 함정**: 모니터 미연결(헤드리스) 상태면 X 세션이 없어 **검은 화면**만 나온다.
  HDMI 더미 플러그나 가상 디스플레이 설정이 따로 필요하다.

### SSH 초기 설정 (1회)
```powershell
# Windows 11 은 OpenSSH 기본 탑재
ssh-keygen -t ed25519
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh <user>@<IP> "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys"
```
`C:\Users\<사용자>\.ssh\config`:
```
Host robot
    HostName <젯슨 IP>
    User <user>
    ServerAliveInterval 30
```
→ 이후 `ssh robot` 만. `ServerAliveInterval` 은 무선 유휴 연결 끊김을 막는다.
