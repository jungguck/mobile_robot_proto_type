## 1. 진단은 아래에서 위로 — 오늘 쓴 사다리

"원격이 되나?" 를 한 번에 묻지 않고 **층을 나눠 아래에서 위로** 올라갔다.
어느 층에서 끊겼는지가 곧 원인이기 때문이다.

```
① 핑          ping -c 2 -W 2 172.30.1.45          → ✅ 같은 망에 살아있다
② 포트 22     bash /dev/tcp 로 접속 시도            → ✅ sshd 는 떠 있다
③ SSH 인증    ssh -o BatchMode=yes robot 'echo OK' → ✅ 키 인증 통과
④ 젯슨 ROS    ssh robot 'echo $ROS_DISTRO'         → ✅ humble, DOMAIN=0
⑤ 노드        ssh robot 'ros2 node list'           → ❌ 없음 (미기동)
⑥ USB 장치    ssh robot 'lsusb; ls /dev/ttyUSB*'   → ❌ 없음  ← 진짜 원인
```

**②의 요령:** `nc` 없이 bash 내장 기능으로 포트만 딱 본다.
```bash
timeout 5 bash -c 'cat < /dev/null > /dev/tcp/172.30.1.45/22' && echo OPEN || echo CLOSED
```
포트는 열렸는데 인증만 거부되면 → **네트워크는 정상, 키 문제**로 범위가 좁혀진다.

**③의 요령:** `BatchMode=yes` 를 붙인다. 비밀번호를 절대 묻지 않고 키로만 시도하므로
프롬프트에서 멈추지 않고 성공/실패가 즉시 갈린다. 스크립트·자동화에 필수다.

> 이 사다리 없이 바로 `robot-up.sh` 를 띄웠다면 "왜 노드가 죽지?" 하고 헤맸을 것이다.
> 실제 원인은 여섯 번째 층(USB)에 있었다.

## 2. SSH — 키는 이미 등록돼 있었다

첫 시도에서 한 번 거부됐다.

```
frlab@172.30.1.45: Permission denied (publickey,password)
```

`ssh-copy-id` 를 다시 돌려보니 **이미 등록돼 있다**고 나왔다.

```
WARNING: All keys were skipped because they already exist on the remote system.
```

확인한 사실:

| 항목 | 결과 |
|---|---|
| PC 키 `~/.ssh/id_ed25519` | passphrase **없음** |
| ssh-agent | 동작 중 (`/run/user/1000/keyring/ssh`), 키 로드됨 |
| 젯슨 `~/.ssh/authorized_keys` | 2줄. **2번째 줄이 이 PC 키** — 지문 `SHA256:QiBa1r...` 일치 |

그 뒤로는 계속 정상 접속된다. **첫 거부의 원인은 규명하지 못했다.**
(`ssh -v` 를 그때 안 찍어서 근거가 없다. 추측은 기록하지 않는다.)
재발하면 `ssh -v robot` 의 `Offering public key` / `Authentications that can continue`
줄을 먼저 볼 것.

> `authorized_keys` 1번 줄 `jk-pc` 는 예전 PC/예전 키다. 정리 대상이지만 급하지 않다.

## 4. "토픽이 안 보인다" ≠ "DDS 가 안 된다"

PC 에서 `ros2 topic list` 가 `/rosout`, `/parameter_events` 만 뱉었다.
09-07 로그가 경고한 docker0 멀티캐스트 문제를 의심할 상황이었지만, **아니었다.**

**가른 방법 — 탐색을 건너뛰고 젯슨 IP 를 직접 지정한다:**

```bash
export ROS_STATIC_PEERS=172.30.1.45   # 멀티캐스트 탐색 대신 이 IP 로 직접
ros2 daemon stop && ros2 topic list
```

이걸로도 결과가 같으면 **네트워크 문제가 아니라 상대가 아예 발행을 안 하는 것**이다.
실제로 `ssh robot 'ros2 node list'` 가 비어 있었다. 부팅만으로는 노드가 안 뜬다 —
`robot-up.sh` 는 수동 실행이고 tmux 세션도 없었다.

**함께 확인한 함정 — `ros2 daemon stop` 을 빠뜨리지 말 것.**
ROS 2 CLI 는 데몬이 탐색 결과를 캐싱한다. 환경변수를 고쳐도 데몬을 재시작하지 않으면
**옛 결과가 그대로 나와서** 환경이 잘못된 줄 알고 삽질하게 된다.

## 6. ⚠️ USB 장치가 전부 빠져 있다 — 09-06 대비 회귀

오늘 젯슨에서 본 `lsusb` 다. 두 번(첫 확인, 재부팅 후) 모두 같았다.

```
Bus 002 Device 002: ID 0bda:0489 Realtek 4-Port USB 3.0 Hub
Bus 001 Device 003: ID 13d3:3549 IMC Networks Bluetooth Radio
Bus 001 Device 002: ID 0bda:5489 Realtek 4-Port USB 2.0 Hub
```

**허브 2개와 블루투스뿐이다.** `/dev/ttyUSB*`, `/dev/ttyACM*` 도 전무하다.

09-06 에는 세 장치가 모두 붙어 udev 별칭까지 잡혀 있었다
(`/dev/motor`, `/dev/rplidar`, `/dev/ttyimu`). **그 사이 물리적으로 분리된 것이다**
(전원 재구성 작업 중). udev 규칙 자체는 젯슨에 남아 있으므로 **다시 꽂으면 별칭도 같이 돌아온다.**

> **허브는 인식되는데 장치가 안 보인다** → 허브 전원은 살아 있고 그 아래가 빈 것이다.
> 의심 순서: ① 모터 보드 전원 ② 허브↔장치 케이블 ③ 업링크만 꽂고 장치는 다른 허브에 물림

**재연결 후 확인 명령:**
```bash
ssh robot 'lsusb; ls -l /dev/ttyUSB* /dev/motor /dev/rplidar /dev/ttyimu'
```

## 7. 전원을 12V 로 재구성

문서(`Relay_Robot_Hardware` 전원 절, 2026-09-06 조사)에 비춰 판단한 내용이다.

| 장치 | 허용 입력 | 12V 에서 |
|---|---|---|
| Jetson Orin Nano 개발자킷 | **DC잭 9–20V** (권장 19V) | ✅ 스펙 안. 정상 동작 |
| DDSM400 ×2 | 정격 **25.2V** | ⚠️ 돌긴 돈다. **최고속도 절반 이하** |
| RPLidar / EBIMU | 5V (USB) | — |

**속도 천장이 낮아질 뿐 토크는 그대로다.** 속도상수 15.9 RPM/V 라 무부하 회전수가
400 RPM → 약 190 RPM, 바퀴 선속도 1.36 m/s → 약 0.65 m/s 가 된다.
토크상수(0.3 Nm/A)는 전압과 무관하다.

> ⚠️ **"로봇이 느리다" 로 기구학 상수를 다시 열지 말 것.**
> `wheel_radius=0.0325` / `wheel_base=0.22` / `rpm_scale=600` 은 2026-09-03 확정값이다.

**지켜야 할 것 — 모터와 젯슨의 전원을 합치지 않는다.**
모터 기동·구속 순간 전류가 튀어 레일이 **9V 아래로 떨어지면 젯슨이 브라운아웃으로 리셋**되고,
SD카드 부팅이라 그게 곧 카드 손상이다. 합쳐야만 한다면 12V 기준 **5A(60W) 이상** +
젯슨 입력단 벌크 커패시터.

**USB 재연결 순서 (권장):** 전부 끄기 → USB 전부 꽂기 → 모터 보드 12V → **젯슨 전원 마지막**.
젯슨이 부팅하며 USB 를 훑을 때 장치가 이미 깨어 있어야 포트가 깔끔하게 잡힌다.
(USB 는 GND 핀이 먼저 닿도록 설계돼 있어 핫플러그 자체는 안전하다. 실패하더라도
"안 잡힘" 으로 나타나지 보통 파손되지 않는다.)

**모터 보드는 전원 사이클마다 `{"T":11002,"type":210}` 초기화가 1회 필요하다** —
전원을 새로 넣었으면 반드시 다시 보낼 것 (`DEBUG_LOG_2026-08-22.md`).

  매 프레임 찍히던 `print("Debug faw data")` 제거 (터미널 폭주 + 시리얼 루프 지연)
- `real_robot_driver_260519.py`: `cmd_vel` 은 **저장만** 하고 10Hz 타이머가 **매 사이클 재전송**.
  `cmd_timeout`(0.5s) 넘으면 0, `feedback_timeout`(0.3s) 넘으면 속도를 0 으로 간주

> 재전송이 stale 자체를 씻어낸다 — `drive()` 안에서 `read_feedback()` 이 매 주기 돌기 때문.

### 12-2. A* 장애물 팽창 + 미탐색 차단

`is_free()` 가 `value == -1 or value < 50` 이었다. 셀 하나만 보니 **로봇 몸통이 벽을 긁는
경로**가 나오고, **미탐색(-1)을 통행 가능으로 취급해 지도 밖으로 경로를 뚫었다.**

`scipy.ndimage.distance_transform_edt` 로 지도가 올 때 **한 번만** 팽창을 계산한다
(계획마다 다시 하지 않는다). `robot_radius`(0.20) + `inflation_margin`(0.05).
결과를 `/inflated_map` 으로 발행 — **PC RViz 에서 "왜 경로가 안 나오는지" 를 눈으로 본다.**

벽 가까이 있을 때 시작 셀이 막혀 계획 자체가 실패하는 걸 막으려고,
반경 안에서 가장 가까운 자유 셀로 대체하는 폴백을 넣었다.

### 12-3. ★ tf2 로 `map` 프레임 일원화 — SLAM 켜는 순간 터지는 구멍

`bridge_node` 는 `/odom`(**odom 프레임**) 위치를 쓰는데 `/global_path` 와 `/mpc_goal` 은
**map 프레임**이었다. 두 노드 어디에도 tf2 import 가 없었다 — 변환 없이 그냥 뺐다.
**Cartographer 가 드리프트를 보정한 만큼(map→odom)이 그대로 추종 오차로 둔갑한다.**

두 노드 모두 `global_frame`(기본 `map`) → `base_link` TF 로 현재 위치를 받게 고쳤다.
`-p global_frame:=odom` 으로 내리면 SLAM 없이도 그대로 돈다.

제어 루프는 젯슨에서 돌아야 하므로(무선 너머 10Hz 는 곧 제어 지터), PC 가 볼 수단이 필요하다.

## 13. ★ QP 가 100% 실패하던 진짜 이유 (측정으로 확정)

리허설 첫 주행에서 로봇이 (0.33, 0.14) 까지 가다 멈추고 **12초간 94번 전부 `QP_FAILED`** 였다.

`x_min = [-2.0, -2.0, -0.3]` 의 θ 한계가 원인이다. 이 값은 tube 만큼 타이트닝되어
**실효 0.25 rad(14°)** 가 된다. 그런데 A* 경로를 따라갈 때 첫 참조점의 접선 방향과
로봇의 현재 방향은 출발 시 쉽게 20~30° 벌어진다 → **첫 사이클부터 제약 위반 → 항상 infeasible.**

추측으로 두지 않고 오프라인으로 재현해 경계를 쟀다:

```
타이트닝된 상태상한 x_b : [1.95 1.95 0.25 ...]
  e_theta=0.20 rad -> OK
  e_theta=0.25 rad -> OK
  e_theta=0.30 rad -> FAIL     ← 경계가 정확히 0.25
  e_theta=0.43 rad -> FAIL     ← 실제 주행 중 관측된 값
```

**해결:** `error_yaw_limit` 파라미터로 빼고 기본값을 `3.2`(사실상 무제한)로.
**heading 오차는 안전 제약이 아니다** — 돌아서 줄이면 되는 값이다. 실제로 지켜야 할 것은
위치 오차(tube)이고 그건 `error_xy_limit` 과 ancillary 되먹임이 담당한다.

**QP 부하는 걱정할 수준이 아니다** (젯슨 우려에 대한 답):
변수 8개 / 제약 40행. PC(i5-12400F) 실측 **평균 4.5 ms, 최대 7.3 ms** — 10Hz 예산의 5%.
대부분이 cvxpy 의 파이썬 오버헤드라 젯슨 ARM 에서 몇 배 느려져도 여유가 있다.
**젯슨이 켜지면 같은 스크립트로 실측할 것.**

## 16. STAGE 2-B 를 왜 따로 뺐나 — IMU yaw **부호**

`ekf.yaml` 은 **방향을 IMU 하나에만 맡긴다** (`imu0_config` 의 yaw 만 true, 바퀴 yaw 는 전부 false).
그래서 **IMU yaw 부호가 반대면 EKF 가 진행 방향을 거울로 뒤집어 적분**하고, 그 `/odom` 이
그대로 SLAM prior 로 들어가 지도가 통째로 망가진다.

**크기가 아니라 부호 문제라 값만 봐서는 눈치채기 어렵다.** 그래서 회전을 직접 시켜 확인한다.
ROS 규약(REP-103)은 반시계(왼쪽) 회전이 +z 다.

**교차 검증 수단이 이미 있다:** `tools/odom_check.py` 의
**② 회전 스케일 = `raw_Δθ / imu_Δyaw`** 가 **음수(≈ −1.0)면 부호 불일치**다.
크기는 맞는데 부호만 틀린 경우를 정확히 잡아낸다.
`rqt_plot /odom_check/raw_theta_deg /odom_check/imu_dyaw_deg` 로 두 곡선이 같은 방향으로
움직이는지 겹쳐 보면 눈으로도 확인된다.

부호가 반대면 `ebimu_publisher.py` 의 `timer_callback()` 에서 `yaw = -yaw` 한 줄.

### ★ 17-1. 경로가 없으면 장애물로 직진했다 (HIGH — 안전)

`robot-up.sh nav` 가 쓰는 조합(`use_goal_topic` + `use_global_path`)에서,
`/mpc_goal` 은 즉시 `goal_pose` 에 들어가는데 `/global_path` 는 아직 없을 수 있다
(계획기 기동 전, 계획기 사망, **A\* 실패**). 그때 옛 코드는 `_generate_reference()` 로
**목표까지 직선 참조**를 만들어 그대로 달렸다 — **지도를 전혀 안 보고.**

A\* 가 "경로 없음"·"목표가 막힘" 으로 실패한 상황이 곧 이 상황이다.
즉 **갈 수 없다고 판정된 목표를 향해 장애물을 뚫고 직진**한다.

→ 경로 추종 모드에서 경로가 없으면 **선다**(`/mpc/status = NO_PATH`, 정지 명령).

**실증:** 장애물 한가운데(1.7, 0.5)를 목표로 주었더니
`Goal cell is not free` → 빈 경로 → `NO_PATH`, `cmd_vel.x = 0.0`, **로봇 안 움직임.**

### 17-2. 낡은 경로를 영원히 붙들었다 (HIGH)

`global_path` 에 수명이 없어서, 계획기가 죽거나 지도에 새 장애물이 생겨도
옛 경로를 계속 `RUNNING` 으로 따라갔다.
→ 계획기가 **실패 시 빈 경로를 발행**하고, MPC 는 `path_timeout`(2s) 넘은 경로를 버린다.

### 17-3. 참조 궤적이 속도 한계의 5~7배로 달아났다 (HIGH)

`step_len = max_v * 0.1` 은 0.01~0.02m 인데 `_advance_along_path` 가 **셀 단위로 스냅**해서
한 스텝에 최소 한 셀(0.05m, 대각 0.07m)을 통째로 넘어갔다. 결과:
**(a)** 예측 모델과 참조가 서로 안 맞고, **(b)** `uRef[0]` 이 항상 `max_v` 에 붙어
**경로가 옆으로 꺾여도 전속 전진 명령**이 나갔다(제자리 회전 대신 튀어나감).
→ 세그먼트 안에서 **보간**(`_path_pose_at`)하도록 교체.
