`my_cartographer.lua:38` 은 원래부터 `use_imu_data = false` 였다.
그런데 `real_robot_driver_260519.py` 는 TF 를 **일부러 안 내고** 있었다.

```python

```

맞는 말이다. 하지만 `ekf.yaml` 은 **yaw 소스가 IMU 단독**이다 (2026-08-22 에 의도적으로
그렇게 바꿨다). 그래서 **IMU 노드만 빼면** EKF 는 방향 소스를 잃고, 드라이버는 TF 를
안 내므로 **`odom → base_link` 가 통째로 끊긴다.** cartographer 는 에러 없이 조용히
아무것도 안 한다. 이것이 IMU-free 로 가는 길을 막던 유일한 실질적 장애물이었다.

### 해결 — `use_imu` 한 스위치로 책임을 옮긴다

| | `odom_topic` | `publish_tf` | `/odom` 발행자 | TF 발행자 |
|---|---|---|---|---|
| **`use_imu:=false` (기본)** | `odom` | `True` | 드라이버 | **드라이버** |
| `use_imu:=true` | `odom_raw` | `False` | ekf_node | **ekf_node** |

launch 는 파라미터만 다른 드라이버 노드 두 벌을 두고 `IfCondition`/`UnlessCondition` 으로
**하나만** 띄운다. `imu_node` 와 `ekf_node` 도 `use_imu` 에 묶였다.

### 덤 — 타임스탬프 이중 취득 종결 (`DEBUG_LOG_2026-09-03.md` 3절 2번)

`publish_odom()` 이 `get_clock().now()` 를 **다시** 불러서 `timer_callback()` 의 적분
시각과 다른 값을 쓰고 있었다. `current_time` 을 넘겨받아 odom 메시지와 TF 가 같은
stamp 를 쓰도록 고쳤다. IMU 없이 scan matching 에만 의존하는 지금은 cartographer 가
그 차이를 자세 오차로 받아들이고, 보정해 줄 다른 센서가 없다.

## 5. 매핑 운용 규칙 — 속도가 IMU 의 대체재다

| 항목 | 값 | 근거 |
|---|---|---|
| 각속도 | **≤ 0.5 rad/s** | S2 가 10Hz(한 스캔 100ms). 1.0 rad/s 면 한 스캔에 **5.7°** 가 번진다. IMU 없이는 포인트별 de-skew 를 할 수단이 없다 |
| 선속도 | **≤ 0.3 m/s** | 같은 이유 (병진 왜곡) |
| 제자리 회전 | **피할 것** | diff drive 에서 바퀴 슬립이 가장 심한 동작. 살짝 호를 그리며 돌 것 |

### ★ teleop 기본 속도 — 속도 제한의 구멍

`robot-up.sh nav` 는 MPC 에 `omega_limit:=0.5` 를 넘기도록 고쳤다. 그런데
**teleop 에는 아무 제한이 없다.** `teleop_twist_keyboard` 기본값은 `speed=0.5 m/s`,
`turn=1.0 rad/s` — 위 한계의 **정확히 2배**다. 매핑은 teleop 으로 하므로 그대로 띄우면
제한이 무의미해진다.

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard \
  --ros-args -p speed:=0.15 -p turn:=0.4
```

GUI(`hw_test`)는 슬라이더가 `to=0.3` 으로 이미 막혀 있어 괜찮다.

### scan matching 이 깨지는 환경 (IMU 로도 크게 못 고친다)

- 긴 특징 없는 복도 — 진행 방향이 구속되지 않는다
- 넓은 빈 홀 — 벽이 `max_range` 밖
- 유리 / 거울 — 반사로 거리가 거짓말을 한다

### 튜닝 — `ceres_scan_matcher.rotation_weight` 40 → 20

초기 추정 각도(= 바퀴 yaw)에서 벗어나는 것에 대한 **벌점**이다. 기본 40 은 초기 추정을
꽤 믿는 값인데, 이제 그 초기 추정이 슬립 잘 나는 바퀴 yaw 하나뿐이다.

- 회전 구간에서 벽이 겹쳐 보이면 → 10 까지 더 내린다
- 특징 없는 복도에서 스캔이 헛돌면 → 40 으로 되돌린다

> `max_range = 8.0` 은 **안 건드렸다.** S2 는 30m 까지 보므로 넓은 공간에서 heading
> 구속이 약하면 12.0 정도로 올려볼 여지가 있다. 실측 후 판단할 것.

## 6. 젯슨이 켜지면 할 순서

```bash
# 1) 빌드 (맨 위 참고 — 이게 안 되면 아무것도 반영 안 됨)
ssh robot "cd ~/mobile_robot_proto_type && git pull && colcon build --symlink-install"

# 2) 오도메트리 + TF 부터 (라이다 없이)
ssh robot "ros2 launch relayrobot_description real_robot_260519.launch.py use_lidar:=false"
ssh robot "ros2 topic hz /odom"                        # 10 Hz
ssh robot "ros2 run tf2_ros tf2_echo odom base_link"   # 출력되면 TF 배선 성공
```

**확인 포인트:** 드라이버 시작 로그에 이 줄이 나온다.

```
Real Robot Driver Started (Wheel Odom Only) — odom_topic=/odom, publish_tf=True
```

`odom_raw` / `publish_tf=False` 로 떠 있으면 `use_imu` 가 true 로 넘어간 것이다.

### 라이다를 먼저 붙여도 되는가 — 된다

cartographer 는 오도메트리가 **정확할** 필요가 없다. `odom → base_link` TF 가
존재하기만 하면 되고, 정확도는 scan matching 이 깎아낸다. 그래서 캘리브레이션을
건너뛰고 바로 SLAM 으로 가도 된다. 위 2)는 건너뛰는 게 아니라 **30초짜리**다.

### 라이다 붙이기 전에 2분만 — 이 두 가지는 보고 간다

안 보고 매핑하면 맵이 깨졌을 때 원인 후보가 넷으로 늘어난다.

**1) 회전 부호** — 좌회전 시 `/odom` 의 yaw 가 **+ 방향으로 증가**해야 한다.

```bash
ros2 topic echo /odom --field pose.pose.orientation
```

`w_enc = (vr - vl) / wheel_base` 이므로 좌회전(+z)이면 오른쪽 바퀴가 더 빨라야 한다.
8/22 에 `DIR_L`/`DIR_R` 로 **전진** 부호는 실측 확정했지만 **회전 부호는 실측 기록이
없다.** 뒤집혀 있으면 cartographer 가 받는 초기 추정이 매 회전마다 반대 방향이고,
IMU 가 없으니 잡아줄 것이 없다.

**2) 라이다 TF / 장착 방향**

```bash
ros2 run tf2_ros tf2_echo base_link lidar_v1_1
```

- 링크가 없으면 → cartographer 가 스캔을 변환 못 해서 **조용히 아무것도 안 함**
- 있는데 회전이 틀리면 → **맵은 그려지는데 통째로 돌아가거나 뒤집혀 나옴**

두 번째가 고약하다. 로봇 정면에 벽을 두고 `/scan` 의 정면 거리(index 0 부근)가 실제와
맞는지 보면 바로 안다. (URDF 실측 불일치 중 **바퀴 간격은 SLAM 에 영향 없고
라이다 위치는 영향 있다.**)

### 그 밖의 검사

| 검사 | 명령 | 틀렸을 때 증상 |
|---|---|---|
| TF 발행자가 하나인가 | `ros2 topic info /tf --verbose` | TF 가 두 값 사이에서 튄다 |
| `use_sim_time` 전부 false | `ros2 param get /cartographer_node use_sim_time` | 시간이 안 맞아 **모든 스캔을 버린다** (에러 없음) |
| 스캔↔TF 지연 | `ros2 topic delay /scan` | `lookup_transform_timeout_sec=0.2` 초과분이 버려진다 |
